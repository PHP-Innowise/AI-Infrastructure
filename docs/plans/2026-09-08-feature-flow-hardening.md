# План: усиление /flow-feature по итогам разбора outstaff-кита

> Статус: план для будущей реализации, не начат. Основание: сравнение
> маршрута `feature` (outstaff-accelerator-kit, слой 3) с нашим
> `/flow-feature` (все четыре готовых издания), 2026-09-08.
> Область: `.claude/commands/flow-feature.md` + `.cursor`-зеркала всех изданий,
> затем прокидка в форджи Infrastructure-Creator (п. 7) — IC генерирует свой
> `flow-feature` для каждого таргета. Точечно — стадии и один новый
> артефактный паттерн. Не редизайн флоу.

## Их маршрут против нашего — честное сравнение

Их фазы: 0 Pre-flight → 1 spec.md → 2 Grilling (опц.) → 3 READY-гейт →
**HUMAN GATE 1 (спека)** → 4 План → **HUMAN GATE 2 (план)** → 5 Реализация
(тесты в том же MR, seam-first, красный тест наблюдается) → 6 Self-review
(две независимые оси) → 7 Verify (команды реально запущены, вывод прочитан) →
8 Черновики (mr.md, tracker-comment.md — публикует человек) → 9 Эволюция (RETRO).
Позвоночник: `tasks/<KEY>/STATE.md` ≤100 строк, переживает границы сессий.

| Их элемент | У нас | Вердикт |
| --- | --- | --- |
| Жёсткая семантика гейта («ход останавливается, не спрошу-и-продолжу») | Есть: checkpoint-стадии в flow-feature требуют STOP и явного ответа | ничего не брать |
| HUMAN GATE 2 (план) | Есть: `checkpoint: plan-approval` | ничего не брать |
| Self-review по двум осям | Есть: `code-reviewer` + `security-reviewer`, `parallel: true` | ничего не брать |
| Verify с реально запущенными командами | Есть: агент `verify`, DOD-требования | ничего не брать |
| STATE.md ≤100 строк | Project Brain governed task + капсула ≤8k — сильнее (ревизии, владельцы, handoffs) | не брать, наше сильнее |
| RETRO / «что выживает из tasks/» | Auto-promotion + turn flush — сильнее (автоматически) | не брать |
| Один тикет = одна сессия, /clear между | Конвенция использования, не механика | максимум строка в docs |
| **0 Pre-flight** (чистое дерево; чекаут занят другим тикетом → worktree) | Нет: Setup только выводит task-id и создаёт governed task | **брать — п.1** |
| **HUMAN GATE 1 + READY-гейт спеки** (каждая строка проверяема, открытые вопросы названы) | Нет: requirements-analyst → сразу architect, первая человеческая точка — только план | **брать — п.2** |
| **8 Черновики** (`mr.md`, `tracker-comment.md` как артефакты; кнопку жмёт человек) | Нет как артефактного паттерна: `finishing-branch` + checkpoint integration, но черновики наружных текстов не материализуются | **брать — п.3** |
| Аварийный выход ≤2 файла без церемонии | Есть мягко («simple tasks → /coder»), без критерия | **брать — п.4, дёшево** |
| Красный тест наблюдается, seam-first | У нас порядок стадий `coder` → `test-generator` — тест после кода | **обсудить — п.5, инвазивно** |
| Grilling (опц. допрос при мутной постановке) | Нет в флоу (brainstorming — отдельный скилл Symfony; grill-me — кандидат Kit 3) | опционально — п.6 |

## Шаги реализации

1. **Pre-flight стадия (фаза 0).** Перед Setup: проверка чистоты рабочего
   дерева; если чекаут занят другой задачей — предложить worktree (скилл
   `using-git-worktrees` уже существует) и записать путь в governed task.
   Грязное дерево само по себе — не блокер: продолжение той же задачи
   легально; чужой WIP сохраняется, а пересечение чужих изменений с
   change set убирает опцию «продолжить» (только worktree/стоп). Записать
   базовое состояние тестов затронутого пакета до первой правки —
   verify дальше сравнивает «не хуже базы», не «всё зелёное» (реальные
   клиентские проекты приходят с красной базой). Правка: frontmatter
   `stages` + раздел Setup в `flow-feature.md`.
2. **Spec-гейт (HUMAN GATE 1) — условный, не безусловный.** После
   `requirements-analyst` — checkpoint `spec-approval`: критерии приёмки
   показываются пользователю, каждая строка проверяема, открытые вопросы
   названы явно. Соразмерность (ревью PR#32): уже согласованный тикет с
   проверяемыми критериями удовлетворяет гейт этим основанием — без
   повторного одобрения (вход M9); когда требования и подход оценимы
   вместе — показать один пакет spec+plan на одно решение. Безусловные
   остановки остаются: открытый продуктовый вопрос или смена объёма →
   стоп зависимой работы с конкретным выбором; действие вне полномочий →
   подготовить проверяемый результат и ждать разрешения. Гейт существует
   для agent-authored спек, а не для пере-подписи уже решённого.
3. **Черновики вместо публикаций (фаза finalization).** `finishing-branch`
   (или новый шаг той же стадии) материализует `tasks/<ID>/mr-draft.md` и
   `tasks/<ID>/tracker-comment-draft.md` — из фактов
   `git log/diff merge-base..HEAD`, с перечнем попавших в диапазон файлов,
   не связанных с тикетом; checkpoint `integration` показывает их.
   Черновики создаются всегда, независимо от того, кто публикует;
   публикация следует выданным полномочиям (posture) и уже данному
   разрешению — без повторного вопроса только из-за смены стадии.
   Синергия: политика `drafts-only` приходит из
   [плана Engagement Posture](2026-09-08-engagement-posture-guardrails.md) —
   этот пункт даёт ей артефакты.
4. **Явный критерий аварийного выхода.** В начале Instructions: «≤2 файлов и
   один промпт → предложи `/coder` и остановись» — вместо размытого
   «simple tasks do not need this flow». Числовой порог — необходимое, но
   недостаточное условие (ревью PR#32: правка авторизации в одном файле
   требует полного маршрута, механическая правка тридцати — нет):
   дополняется квалификатором «нет поверхности security/schema/infra,
   изменение обратимо»; при сомнении — полный маршрут.
5. **Порядок тест/код — решено (ревью PR#32).** Цикл
   «падающий тест → фикс → прогон» ведёт **один исполнитель** (`coder`
   начинает с наблюдаемо падающего теста); `test-generator` остаётся
   отдельной стадией **после** — ищет пропущенные сценарии, а не пишет
   первый тест. Перестановка стадий сама по себе TDD не доказывает; для
   док-правок — соразмерные проверки, не полный цикл. Формулировки
   капсулы `coder` — с учётом TDD-семантики каждого издания.
6. **(Опционально) Grilling-стадия.** Необязательная интеррогация между
   requirements и spec-гейтом, включается только при мутной постановке.
   Кандидаты: собственный скилл по мотивам, или `grill-me` через Kit 3
   (статус в реестре: NOT REVIEWED — сначала досье). Протокол —
   **frontier**, не «по одному вопросу»: задаётся весь текущий фронтир
   дерева решений одним нумерованным раундом, каждый вопрос с
   рекомендованным ответом; ответы перестраивают дерево и открывают
   следующий раунд; факты — работа агента (субагенты, не блокируя
   остальной фронтир), решения — человека; готово, когда фронтир пуст.
   Измеренный урок прототипа: batch-раунды быстрее последовательных
   вопросов при том же качестве решений.
7. **Паритет generated vs hand-built (обязательный follow-up).**
   Infrastructure-Creator генерирует собственный `flow-feature` для каждого
   таргета (`command-forge` + `skill-flow-composer`, компиляция из canonical
   plan graph) — подтверждено живым таргетом. Пп. 1–4 обязаны быть прокинуты
   в контракты этих форджей, иначе рукописные издания получат spec-гейт и
   pre-flight, а сгенерированные акселераторы — нет, и разрыв будет молча
   воспроизводиться каждым `infra-generate`/`infra-update`. Выполняется
   после пп. 1–4 (форджам нужен готовый образец из изданий); тот же разрыв
   класса «Stage A–C в форджах» уже отслеживается в BACKLOG.

## Порядок и рамки

- Пп. 1–4 — одна связная правка `flow-feature.md` на издание; сначала
  `PHP Core` (правило репозитория: универсальные изменения сначала там),
  затем адаптация в Laravel/Symfony/WordPress с учётом их семантики.
- Каждое издание: `build_mirrors.py --write`, свой `CHANGELOG.md`,
  прогон тестов издания.
- П. 5 — отдельным решением после пп. 1–4.
- `flow-review` не трогаем: у них аналога-находок для него из этого разбора нет.

## Что сознательно НЕ берём

STATE.md-позвоночник и RETRO-ритуал (наши Project Brain / auto-promotion
объективно сильнее для командной работы), дисциплину «/clear между тикетами»
(конвенция, не механика), их модель невидимости (закрыта планом Engagement
Posture другим способом).
