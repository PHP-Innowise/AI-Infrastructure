> Статус: план для будущей реализации, не начат. Решение зафиксировано
> 2026-09-08: упростить + маршрутизация; не удалять, не ждать измерений.
> Область: `harness/` этого репозитория (канон: `harness/src/harness/sdd.py`,
> `sessions.py`, `web.py`, README, `tests/test_harness_sdd.py`); синхронизация
> в форк AI-Infrastructure — отдельным шагом после.

## Проблема

Жалобы пользователей: «задачи с SDD делаются очень долго». Причина
структурная, видна из кода, а не из ощущений:

1. Шесть фаз, каждая — отдельный запуск провайдера с ручным ревью между.
2. Implement останавливается на **каждом** чекпоинте tasks.md → фича с
   четырьмя чекпоинтами = 8–10 сессий суммарно.
3. Нет аварийного выхода: маленькая фича проходит ту же церемонию, что и
   большая. `[NEEDS CLARIFICATION` жёстко блокирует все дальнейшие фазы.
4. Дублирование с `/flow-feature` (обе: понимание → план с одобрением →
   реализация → верификация); после реализации плана
   [feature-flow-hardening](2026-09-08-feature-flow-hardening.md)
   дифференциатор сожмётся ещё сильнее.

## Почему не удалять

- Долговечные документы: `specs/<feature>/sdd-*.md` с регистрацией в
  MANIFEST — living specs; flow-feature пишет только рабочие `tasks/`.
- Единственный механизм **многосессионных** фич: `progress.md` +
  «resume the first unfinished task».
- Встроенная test-first дисциплина.

Ниша SDD — большие фичи, не влезающие в одну сессию, и фичи, требующие
долговечной спеки. Проблема в том, что она не отличает их от маленьких.

Проверено по `sdd.py` построчно. **Большинство пунктов SDD уже содержит —
в более жёсткой форме, чем план 2 добавляет в flow-feature:**

| Пункт плана 2 | Вердикт для SDD |
| --- | --- |
| Spec-гейт | Уже есть, жёстче: `[NEEDS CLARIFICATION` — серверная блокировка в `check()`; каждая фаза ревьюится человеком. План 2 импортирует дисциплину SDD в flow-feature, не наоборот. |
| Красный тест до кода | Уже есть: tasks.md «test-before-implementation», implement «write and run failing tests before implementation». П. 5 плана 2 заимствовать отсюда. |

## Шаги реализации

1. **Правило маршрутизации по размеру.** Одна формулировка в трёх местах:
   README-секция SDD, подсказка селектора Workflow в UI, docs/
   ORCHESTRATOR-COMMANDS.md. «Тривиально (≤2 файла) → `/coder`; обычная
   фича, одна сессия → `/flow-feature`; большая/многосессионная фича или
   нужна долговечная спека → SDD». Симметрично аварийному выходу плана 2.
2. **Lite-трек: объединённая фаза Specify+Plan.** Новая фаза `spec-plan`
   (один запуск пишет оба документа) для фич ниже порога; `REQUIRED`
   для tasks принимает результат обеих дорожек. Полная дорожка остаётся
   без изменений для больших фич.
3. **Настраиваемая гранулярность чекпоинтов Implement.** Настройка
   `stop_mode: every-checkpoint | end-of-run` (журнал всех чекпоинтов в
   progress.md, остановка в конце). Умолчание — `every-checkpoint`
   (текущее поведение, безопасное); `end-of-run` — осознанный выбор в UI.
4. **Предупреждение о грязном дереве** при запуске Implement в текущем
   чекауте (не worktree) — предупреждение, не блокировка: harness уже
   показывает Git-статус, но не обращает на него внимание при старте фазы.
5. **Черновики (порт из плана 2).** Финальный чекпоинт Implement и/или
   Review дополнительно материализуют `specs/<feature>/sdd-mr-draft.md`;
   наружу публикует человек. Согласовано с
   [engagement-posture](2026-09-08-engagement-posture-guardrails.md)
   `external_actions: drafts-only`.
6. **Позиционирование Review-фазы.** Не удалять (проверка против критериев
   приёмки — отдельная ценность), но в описании фазы и README разграничить
   с flow-review/Fleet: Review = acceptance-критерии спеки, Fleet/flow-review
   = качество кода. Сейчас три ревью-механизма выглядят взаимозаменяемыми.
7. **Тесты и доки.** `tests/test_harness_sdd.py`: `spec-plan`-фаза,
   `stop_mode`, маршрутизационные подсказки; README-секция SDD переписана
   под lite/full дорожки.
8. **Синхронизация форка.** Перенос в AI-Infrastructure — после приёмки
   здесь (форк уже расходится; сверить перед портом).

## Вне объёма

- Удаление SDD (пересмотреть после данных adoption-review — план 3
  покажет реальное использование lite vs full дорожек).
- Автоматическое определение размера фичи (порог выбирает человек).
- Слияние SDD с flow-feature в один механизм.
