# План: cost-aware model routing — план-гейт и ограниченная эскалация

> Статус: план для будущей реализации, не начат. Решения по развилкам
> зафиксированы 2026-09-11. Основание: разбор AI-инфраструктуры
> разработчика на проекте SmileExpress (`ai-infrastructure-overview.md`,
> ревью 2026-09-11) — паттерн признан слоем, которого у изданий нет,
> и взят в перенос.

## Проблема

Роутинг моделей в изданиях сегодня только статический: frontmatter
`model:` у агентов (`opus`: architect, brainstorming, code-reviewer,
council, review-pr, systematic-debugger, security-reviewer; `sonnet`:
исполнители; `haiku`: documentation-generator, memory-bank, release,
using-git-worktrees — ярус уже трёхуровневый). Динамики поверх него нет:

1. **Нет план-гейта.** Ничто не фиксирует правило «утверждённый план
   есть → исполнение остаётся на дешёвой модели и не возвращается к
   дорогой, кроме как по протоколу».
2. **Эскалация — только текстовая, и уже расходится.** «Три неудачные
   попытки → `systematic-debugger`» (скилл test-generator) против
   «→ `/debugger`» (`DOD.md:87`) — два написания одного правила, без
   контракта контекста и без потолка раундов: эскалированный opus-агент
   получает столько контекста, сколько передаст вызывающий, хоть всю
   беседу. Хуже: на «план не покрывает» у `/flow-feature` сегодня
   единственный маршрут — «стоп + предложи `/debugger`» — design-gap
   уходит в инструмент для багов.
3. **Нет правила о выходе эскалации.** Результатом должна быть правка
   плана и записанное решение, а не патч кода в обход плана.
4. **Граница план-агентов не задокументирована — и это главная статья
   расхода.** `writing-plans-agent` — sonnet, при живом `architect-agent`
   (opus); когда план задачи требует архитектурного суждения — нигде не
   сказано. При этом `/flow-feature` **хардкодит обе** planning-стадии:
   architect (opus) гоняется на каждой фиче, включая рутинные.
   Неформальное «skip a stage that clearly does not apply» оставляет
   решение на усмотрение модели без критерия. Правило только в описаниях
   агентов зашитую последовательность стадий не изменит.

Прототип (SmileExpress) показывает рабочую форму: дорогая модель пишет
план один раз; исполнение — дешёвая; затык → ограниченная эскалация
(максимум 2 раунда), эскалированная модель видит только план + причину
эскалации + diff — никогда полную беседу.

## Что уже есть (prior art — расширяем, не дублируем)

| Существующее | Отношение к плану |
| --- | --- |
| `model:` frontmatter всех агентов изданий | Статическая половина роутинга готова; план добавляет только динамический протокол поверх. Новых model-полей не изобретать. |
| «3 попытки → systematic-debugger» (test-generator) / «→ /debugger» (DOD.md) | Зародыш эскалации; протокол формализует то же движение (bounded, вверх по цене) и добавляет контракт контекста. Не заменять — но унифицировать написание и развести с plan-escalation явным критерием (см. решения). |
| [sdd-simplification](2026-09-08-sdd-simplification.md) п. 1 — маршрутизация по размеру | Ось «какой флоу» (тривиально → /coder; фича → /flow-feature; большая → SDD). Наша ось — «какая модель внутри флоу». Компонуются; trivial-bypass прототипа уже закрыт там — не дублировать. |
| `cost_attribution.py` | Готовая ось измерения «доля opus-токенов до/после» — прототип свой роутинг числом не доказывает, мы можем. |
| Harness: каталог моделей в UI (`providers.py`) | Выбор модели на сессию, не политика. Не трогать в v1. |

## Зафиксированные решения

| Развилка | Решение |
| --- | --- |
| Форма | Не новый агент — протокол: скилл `plan-escalation` + MUST-блок в `AGENTS.md`. Исполняет существующий `architect-agent` (уже opus). Thin-agent модель сохранена: один агент — один скилл. |
| Контракт контекста | Вход эскалации строго: активный план (`tasks/TASK-NNN`), причина эскалации, diff. Полная беседа — никогда; правило в тексте скилла как MUST NOT. |
| Потолок | 2 раунда эскалации на задачу, затем блокирующий human gate. Симметрично «3 попыткам» DOD — числа не унифицировать искусственно, но сослаться друг на друга. |
| Выход эскалации | Правка плана + запись решения (decision в Project Brain / план-документ). Не код: имплементацию по обновлённому плану продолжает исполнитель на sonnet. |
| writing-plans vs architect | Frontmatter не менять. В описания обоих агентов — правило выбора: план обычной задачи — writing-plans (sonnet); план, требующий архитектурного суждения (новые границы модулей, интеграции, схемы данных), — architect (opus), один раз. **Плюс architect-стадия в `/flow-feature` становится условной по тому же критерию** — правило в описаниях агентов зашитую последовательность не меняет, а именно безусловная architect-стадия и есть основная статья opus-расхода на рутинных фичах. |
| Развод двух эскалаций | После реализации путей вверх два, критерий выбора пишется в оба текста: **падает известное поведение (тест, ошибка) → systematic-debugger; нужно решение, которого нет в плане → plan-escalation.** Без явного критерия исполнители выбирают наугад, и adoption-review покажет кашу. Заодно унифицировать написание debugger-эскалации между test-generator и DOD. |
| Scope v1 | `PHP Core` сначала (per contributing conventions), затем адаптация Laravel/Symfony/WordPress — у WordPress состав opus-агентов уже отличается (нет architect/code-reviewer в opus-списке), сверить перед портом, не копировать вслепую. Codex — текстом политики в `AGENTS.md` (слоя агентов нет). |

## Принципы, перенятые из прототипа как есть

- **Дорогая модель — только где зарабатывает свою цену:** архитектурные
  решения, тяжёлые баги, изменение плана. Всё остальное — дешёвая.
- **Минимальный контекст эскалации.** Bounded-вызов дешёв не только
  раундами, но и входом: план + причина + diff.
- **Потолок, затем человек.** Третьего раунда нет; двух не хватило —
  значит, проблема не в модели.
- **Эскалация меняет план, а не обходит его.** Иначе план перестаёт быть
  источником правды и план-гейт умирает.

## Шаги реализации

1. **`PHP Core`: скилл `plan-escalation`** (канон `.agents/skills/`):
   триггер (исполнитель упёрся в не покрытое планом решение), вход
   (контракт контекста), процедура (постановка вопроса → architect-agent →
   правка плана → запись решения), лимит 2 раунда, выход (обновлённый
   план, human gate при исчерпании). Формат — как у существующих скиллов
   издания.
2. **`AGENTS.md` + `DOD.md` `PHP Core`:** MUST-блок роутинга — план-гейт
   (имплементация утверждённого плана не меняет архитектуру молча),
   эскалация только через `plan-escalation`, потолок, контракт контекста,
   критерий развода эскалаций (баг → debugger, design-gap →
   plan-escalation). Правило выбора writing-plans vs architect — в
   описания обоих агентов. В `DOD.md` — тот же критерий развода и
   унификация существующего расхождения (`/debugger` в DOD:87 vs
   `systematic-debugger` в test-generator — одно правило, одно написание).
3. **`/flow-feature`: две правки стадий.** (а) Architect-стадия становится
   условной: выполняется только при критерии архитектурного суждения
   (новые границы модулей / интеграции / схема данных), иначе planning
   начинается с writing-plans — это основной источник экономии opus, без
   него план не «cost-aware». (б) Точка эскалации: «план не покрывает
   решение → plan-escalation» вместо сегодняшнего «стоп + предложи
   /debugger» для design-gap. Согласовать с
   [feature-flow-hardening](2026-09-08-feature-flow-hardening.md)
   (аварийный выход) — не породить второй конкурирующий выход.
4. **Порт в Laravel/Symfony/WordPress** с адаптацией под их состав
   агентов; `build_mirrors.py --write` по каждому изданию;
   `--verify-inventories` → `--write-inventories` (новые файлы скиллов
   входят в устанавливаемый payload) → re-verify.
5. **Тесты:** в существующие тесты изданий — проверка, что скилл
   присутствует во всех четырёх изданиях и зеркалах, что `AGENTS.md`
   содержит блок роутинга, и что текст скилла содержит потолок и MUST NOT
   полной беседы (строковые инварианты, по образцу существующих
   semantics-тестов).
6. **Changelogs:** записи в `CHANGELOG.md` каждого затронутого издания
   (изменение не в shared core). DOD каждого издания прогнать.
7. **Измерение:** `cost_attribution.py` на потребляющем проекте до/после —
   доля opus-токенов; цель — снижение без роста числа ре-имплементаций.
   Без измерения пункт не закрывать: прототип продаёт роутинг словами,
   мы должны числом.

## Вне объёма v1

- **IC-форджи** (agent-forge/skill-forge генерируют протокол в bespoke
  акселераторы) — v2 после приёмки в изданиях; иначе generated снова
  отстанет от hand-built (тот же паттерн, что Stage A–C гэп в BACKLOG §2).
- **Harness-роутинг** (модель на фазу SDD: spec-plan — opus, implement —
  sonnet) — отдельным шагом после sdd-simplification, чтобы не
  конфликтовать с его правками `sdd.py`.
- **Автоопределение** «архитектурная vs рутинная» — порог выбирает
  человек, как и в sdd-simplification.
- **Смена модели в основной беседе** — Claude Code этого не даёт; роутинг
  живёт только на границах субагентов, и это честно сказать в скилле.
