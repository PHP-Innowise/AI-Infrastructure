## 1. Общий контракт полномочий и остановок

Проектные полномочия задают предел действий агента. Согласование задачи
определяет её цель, объём и допустимые изменения внутри этого предела.
Проверка результата определяет, можно ли считать работу завершённой.
Эти три решения следует хранить и проверять отдельно.

Одобрение требований или плана сохраняет силу между стадиями и сессиями,
пока не меняются их существенные условия. Запись должна связывать одобрение
с версией артефакта или явным объёмом задачи, источником решения и границами
полномочий. При изменении условий повторно согласуется затронутая часть.

| Ситуация | Предлагаемое поведение |
| --- | --- |
| Есть согласованный тикет с проверяемыми критериями; существенных вопросов нет | Использовать его как основание; не запрашивать повторное одобрение той же спеки |
| Требования и технический подход можно оценить вместе | Показать один пакет для решения вместо двух последовательных остановок |
| Не решён вопрос о поведении продукта, меняется объём или существенный риск | Остановить зависимую работу и представить конкретный выбор с последствиями |
| Требуется действие за пределами полномочий | Подготовить доступную для проверки часть и остановиться до разрешённого решения |
| Нужен обычный локальный выбор внутри принятого плана | Продолжить работу и записать значимое решение; не эскалировать каждую деталь |
| Возник блокер проверки | Выполнить доступную диагностику; при невозможности получить необходимое доказательство остановиться и назвать пробел |

Режим прохождения обычных чекпоинтов не отменяет эти остановки, явную отмену
пользователя или ограничения бюджета. Уже полученное разрешение не следует
запрашивать повторно только из-за смены агента или фазы.

## 2. Engagement Posture: область действий и гарантии

Первая реализация остаётся в Infrastructure-Creator. Поля профиля описывают
действие, область ресурсов и окружение: например, миграции локальной тестовой
БД и миграции production имеют разные разрешения. Неоднозначное или отсутствующее
разрешение не открывает рискованную операцию; доступная работа в пределах
известных разрешений может продолжаться.

Минимальный профиль должен различать:

- право изменять файлы, коммитить, отправлять ветку и публиковать внешние тексты;
- разрешённые операции автоматизации и их окружения;
- размещение инфраструктуры: общая в репозитории или локальная;
- допустимые данные и получателей: исходники, диагностические данные,
  внешняя модель, поиск, MCP/API и телеметрия.

Термин `local-only` нельзя принимать без определения: запрет сетевых действий
инструментов и запрет отправки данных облачной модели — разные ограничения.
Требование локальной обработки должно проверяться до передачи защищённых
данных провайдеру. Хук внутри уже запущенной облачной сессии этого не обеспечивает.
Если выбранный клиент не может обеспечить требование, генератор сообщает
несовместимость и не выдаёт профиль за соответствующий ограничениям.

Ответы допускается собирать одним структурированным блоком. Каждый ответ
сохраняется отдельно; обязательность полей, происхождение решения и таблица
«решение → артефакты → проверка» защищают от пропусков. Изменение позы при
обновлении требует отдельного явного решения, молчаливого расширения прав нет.

«Локальная установка без включения в репозиторий» использует Git exclude для
собственных неотслеживаемых файлов и сохраняет tracked-файлы клиента. Это
ограниченная гарантия состава Git-изменений. Она не обещает конфиденциальность
локальных файлов, промптов или сетевого обмена. Git прямо указывает, что
правила игнорирования не действуют на уже отслеживаемые файлы:
[документация gitignore](https://git-scm.com/docs/gitignore).

Для каждого выбранного клиента проверяются доступные каналы действий.
Правило публикации относится и к CLI, и к подключённому API/MCP. Хуки
проверяют детерминированные события, а поведенческие ограничения отражаются
в политике и приёмочных сценариях. Отчёт различает технически обеспеченную
гарантию, инструкцию агенту и неподдерживаемое ограничение. Конфликт с уже
существующим tracked-конфигом решается до публикации установки.

Готовые издания и отдельная оболочка рабочего окружения остаются за пределами
первого этапа; контракт должен допускать их последующее подключение.

## 3. Feature flow: проверки без повторного согласования

Pre-flight фиксирует ветку, рабочий каталог, исходные изменения и область
задачи. Наличие dirty-файлов само по себе не означает конфликт: нужно отличать
продолжение текущей задачи от чужой работы. При конфликте задач используется
изолированный worktree; чужие изменения не сбрасываются и не включаются в коммит.

Маршрут выбирается по неопределённости, последствиям ошибки и потребности
в долговечных артефактах. Число файлов и предполагаемая длительность могут
быть подсказками, но не разрешением обходить необходимые проверки.

| Потребность | Маршрут |
| --- | --- |
| Понятное локальное изменение в существующем контракте | Прямой исполнитель с соразмерной проверкой |
| Несколько согласованных стадий разработки | `flow-feature` с общей политикой остановок |
| Спецификация должна жить после задачи и служить основой приёмки | SDD независимо от размера изменения |

Проверяемые критерии нужны во всех маршрутах; отдельный spec-гейт включается
по контракту раздела 1. Architect вызывается при новом архитектурном решении,
а не при каждом прохождении planning. При сомнении исполнитель сначала
проверяет существующие ограничения и приводит основание выбора маршрута.

Для изменения поведения исполнитель выполняет цикл теста и реализации
в одном контексте, когда такой тест технически применим. Отдельный
`test-generator` ищет пропущенные сценарии. Перестановка стадий сама по себе
не считается доказательством test-first работы; нужны результаты запусков.
Для документации и иных изменений без подходящего исполняемого теста выбирается
соразмерная проверка с объяснением её границ.

Черновики MR и сообщения трекеру создаются как проверяемые рабочие артефакты
в `tasks/` с действующим префиксом скилла. Если публикация разрешена в текущем
объёме, агент может её выполнить. При `drafts-only` передаёт готовые тексты
человеку. Это правило одинаково для flow-feature и SDD.

Project Brain и auto-promotion сохраняют решения и знания. Для повторяющихся
ошибок отдельно нужен краткий разбор причины и изменения процесса; наличие
автоматического сохранения ещё не доказывает, что такой разбор состоялся.
Новый обязательный RETRO-ритуал для каждой задачи не вводится.

## 4. Adoption review: возможность использования и результат

Сначала инструмент отвечает на три разных вопроса: была ли поверхность
доступна, была ли подходящая задача, дал ли вызов полезный результат.
Для release-скилла отсутствие релизов в окне наблюдения означает отсутствие
возможности оценить его применение, а не основание удалить его.

Детерминированный слой собирает события и ссылки на эпизоды. Оценка подходящих
задач, отдачи и причин отказа выполняется отдельно, с доказательством и уровнем
уверенности. Отказ из-за полномочий или прерывание сессии не равны отказу
пользователя от самого инструмента. Used/Dormant/Rejected — выводы этого слоя;
при недостатке данных остаётся Unknown.

Минимальный отчёт содержит:

- окно наблюдения, версии установленного payload и покрытые клиенты;
- доступность, наблюдаемые возможности применения, попытки и успешные исходы;
- стоимость, задержки, вмешательства человека и переделки, если они измеримы;
- доказательства, неизвестные данные и уровень уверенности в рекомендации.

Доступность определяется для конкретной поверхности и версии клиента с учётом
области загрузки; простого равенства `cwd` корню проекта недостаточно.
Читатель транскриптов сохраняет вызовы инструментов и их результаты;
дедупликация биллинга выполняется отдельно. Учитываются оба имени инструмента
делегирования, `Agent` и `Task`. Блокировки хуков — отдельная метрика.

В v1 допустимо покрыть только Claude Code и явно указать ограничения.
Выводы о SDD и выборе stop-mode по всем провайдерам требуют событий самого
Harness. Неполное покрытие нельзя использовать для решения о судьбе всего SDD.
Две недели — ориентир запуска аудита, а достаточность данных определяется
наблюдаемыми возможностями применения и разнообразием задач.

Порядок рассмотрения рекомендаций: исправление триггера или содержания,
объединение дубликатов, загрузка по требованию, затем обоснованное удаление.
Редкость полезной функции сама по себе не является дефектом. Запретительные
правила не удаляются за отсутствие срабатываний. Экономия байтов дескриптора
показывается отдельно от измеренной экономии стоимости и времени задачи.

Аудитор остаётся инструментом этого репозитория вне устанавливаемого payload.
Отчёты по умолчанию содержат агрегаты и локальные ссылки. Цитаты включаются
явно и остаются в игнорируемом локальном выводе; передача транскриптов модели
подчиняется профилю данных. Рекомендации применяются только по решению человека.

## 5. SDD: один workflow с настраиваемыми остановками

Первый этап сохраняет один SDD, существующие документы и возможность resume.
Объединённая подготовка Specify+Plan создаёт те же артефакты, что раздельные
фазы, когда существенные требования уже ясны. Нерешённые требования сохраняют
блокировку зависимой работы. Legacy-пути и существующие сессии продолжают
работать без обязательной миграции документов.

`every-checkpoint` остаётся совместимым умолчанием. Явно выбранный `end-of-run`
разрешает проходить обычные чекпоинты внутри реализации, записывая прогресс,
проверки и решения. Обязательные причины остановки из раздела 1 действуют
в обоих режимах. Перезапуск сессии не стирает выбор режима, предел бюджета
или невыполненные задачи. Режим не запускает следующие фазы автоматически.

Review проверяет реализацию против критериев спецификации. Анализ качества
кода и безопасности может дополнять его; различие целей не требует всегда
запускать все механизмы ревью подряд. Черновики внешних сообщений остаются
рабочими артефактами, а долговечная спецификация — источником критериев.

Отдельный продуктовый режим SDD-lite пока отложен. Вернуться к нему можно,
если пилот покажет потребность, которую не закрывают настраиваемый SDD и
flow-feature. Длительность одной сессии не определяет эту потребность.

## 6. Роутинг моделей: проверяемый пилот

Первый эксперимент сравнивает обязательную и условную architect-стадию на
сопоставимых задачах. Обычный план выполняется внутри существующих решений;
новые границы модулей, интеграции, схема данных или существенный риск дают
основание привлечь архитектора. Выбор подтверждается контекстом задачи.
Конкретные модели фиксируются в конфигурации пилота; результат одной пары
моделей не объявляется универсальным правилом всех провайдеров.

В этом сравнении остальные условия фиксируются, включая правила обработки
блокеров, контекст и лимиты. Описанный ниже протокол эскалации проверяется
отдельным следующим экспериментом при неизменной выбранной конфигурации
роутинга. Одновременное изменение двух механизмов не даёт основания приписать
экономию условному вызову architect.

План фиксирует критерии, границы и значимые решения. Локальные детали
реализации в этих пределах не требуют эскалации. Изменение согласованного
контракта отражается в плане и проходит необходимое согласование.

Эскалацией управляет основной оркестратор. Исполнитель возвращает блокер,
архитектор выполняет свой существующий скилл. Затем оркестратор вызывает
существующую стадию `writing-plans` для внесения решения в активный план
и организует запись решения в Project Brain. При существенном изменении
согласованного контракта он получает необходимое одобрение перед возвратом
к реализации. Новый скилл-протокол, если он понадобится,
не меняет молча `invokes` существующего агента и не разрешает цепочки внутри
субагентов. Диагностика ошибки может выявить design-gap и наоборот; результат
диагностики позволяет сменить маршрут с сохранением истории блокера.

Передаётся ограниченная Task Capsule со ссылками на активный план, критерии,
релевантные файлы и сохранённые доказательства проверки. При необходимости
агент открывает конкретный источник. Полная беседа и сырой diff
не передаются. Нехватку необходимых доказательств нельзя выдавать за экономию.

Для отдельного эксперимента с эскалацией предлагаемый стартовый предел —
две попытки по одному блокеру и отдельный
конечный бюджет всей задачи, выбранный перед пилотом. Смена агента, названия
или сессии не обнуляет повторные попытки той же проблемы. При исчерпании
предела оркестратор показывает результаты и следующий выбор человеку.
Недостаток двух попыток не доказывает, что причина не связана с моделью.

## 7. Измерение, этапы и критерии приёмки

До изменения workflow фиксируются исходные данные на потребляющем проекте.
Для сравнения сохраняются класс и риск задачи, объём критериев, версии моделей,
политики, предоставленные инструменты и лимиты. Расход включает дочерние вызовы,
повторы и неуспешные попытки. При отсутствии денежных данных показываются
измеренные токены и явно обозначенная оценка, без утверждения о точной цене.
Отчёт показывает покрытие usage и число вызовов с неизвестными расходами.
Пропуски не считаются нулём; при них нельзя заявлять измеренную полную
стоимость или доказанное снижение расходов без оценки влияния этих пропусков.

Основной показатель пилота — все расходы на выбранную группу задач, включая
незавершённые и отвергнутые, делённые на число принятых задач при сопоставимом
качестве. При отсутствии принятых задач показатель не определён; публикуются
расходы с указанием покрытия и число принятых задач, равное нулю.
Вместе с ним показываются доля принятых задач, дефекты, переделки, полное время
до результата, время ожидания человека и количество вмешательств.
Доля токенов дорогой модели и число фаз — диагностические показатели.
Стоимость времени человека не смешивается с оплатой провайдера без явно
согласованной методики. Размер выборки и неопределённость видны в отчёте.

До запуска пилота команда выбирает сопоставимые задачи, единые критерии приёмки,
предел расходов и допустимые изменения метрик качества. Без этих условий
отчёт остаётся наблюдением и не служит основанием для массового внедрения.

| Этап | Область будущей реализации | Условие завершения |
| --- | --- | --- |
| A. Общий контракт и исходные измерения | Полномочия, матрица остановок, схема событий и пилот на одном потребляющем проекте | Зафиксированы проверяемые разрешения, правила сохранения одобрений и исходные показатели |
| B. Pre-flight и остановки | Универсальные правила сначала в PHP Core, затем адаптация остальных изданий; posture в IC | Нет повторного согласования неизменённых решений, чужие изменения сохранены, обязательные остановки срабатывают |
| C. Отчёт adoption и настраиваемый SDD | Репозиторный аудитор; `harness/src/harness/sdd.py`, sessions и UI | Разделены неизвестность и отсутствие применения; оба stop-mode и resume проходят сценарии; старые сессии совместимы |
| D1. Пилот model routing | Условный architect в выбранном издании при неизменной обработке блокеров | Есть сравнение стоимости и качества; решение о расширении опирается на критерии пилота |
| D2. Пилот эскалации | Новый протокол на задачах с блокерами при зафиксированной после D1 конфигурации роутинга | Отдельно измерены исходы блокеров, расходы и соблюдение лимитов; эффект не приписывается D1 |

Образцы flow-feature после приёмки переносятся в контракты IC-форджей отдельным
проверяемым шагом этапа B. До этого generated-паритет не объявляется достигнутым.
Роутинг в IC и отдельный SDD-lite остаются отложенными решениями.

Обязательные приёмочные сценарии будущей реализации:

1. Изменение авторизации в одном файле получает необходимые проверки;
   механическое изменение многих файлов не вызывает архитектора без причины.
2. Согласованный тикет проходит без повторного spec-гейта; изменение объёма
   вызывает адресное согласование и обновляет сохранённое основание.
3. Локальная миграция разрешена, production запрещена; пустой список разрешений
   не открывает операции. Публикация через CLI и подключённый API следует одной позе.
4. Чужие staged/unstaged-файлы и локальный конфиг сохранены; конфликт установки
   с tracked-политикой обнаруживается до записи.
5. Нет релизов — нет вывода о бесполезности release-скилла; пропущенные события,
   неподдерживаемый клиент и отказ по полномочиям отражаются явно.
6. `end-of-run` проходит обычный чекпоинт, сохраняет прогресс и останавливается
   при изменении требований, исчерпании бюджета или запрете операции.
7. Эскалация получает необходимые доказательства, сохраняет счётчик при resume
   и возвращает задачу исполнителю в пределах обновлённого плана.

Сквозной сценарий: согласованный тикет выполняется с разрешёнными локальными
коммитами, запрещёнными push и публикацией, совместимым локальным провайдером
и режимом `end-of-run`. Обычный чекпоинт сохраняется без повторного вопроса.
Обнаруженная необходимость внешней интеграции останавливает зависимую работу;
агент предъявляет решение и готовые черновики, не выполняя запрещённые действия.
Отчёт сохраняет причины остановки, исход и расходы без сырого текста промптов.

Валидация использует события, результаты проверок и состояние артефактов.
Наличие нужной фразы в Markdown не заменяет проверку поведения агента.
Детерминированные сценарии входят в тесты; проверки реального поведения модели
проводятся отдельно на разрешённом пилоте с учётом стоимости.
