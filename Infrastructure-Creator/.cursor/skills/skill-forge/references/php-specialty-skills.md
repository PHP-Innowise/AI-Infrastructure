# PHP Framework-Specialty Skills Reference

These skills are **conditional**: `skill-forge` generates one only when the profile's section **3.1 (Framework-Specialty Signals)** marks the matching signal `confirmed` or `inferred` (never for `unknown`/`none`). Each row below generalizes a pattern that the Laravel and/or Symfony accelerators in this monorepo implement as a *framework-named* skill (e.g. `eloquent`, `messenger-designer`) into a *signal-named* skill that fits whatever ORM/queue/admin-panel/etc. the target actually uses - Eloquent, Doctrine, a bare PDO repository layer, RabbitMQ, SQS, or anything else the evidence points to. Never name a generated skill after a framework the target does not use; name it after the generic concept and ground its body in the target's real package/tool.

Like all non-runtime-fixed candidates, these are NOT generated by default - each requires its own evidence line in section 3.1.

## The Specialty Catalog

| `form-validation-design` | Structured input validation beyond simple inline rules - a dedicated Form/Request/DTO + Validator layer with custom constraints or validation groups. | Choosing and implementing the validation architecture: custom constraint/rule classes, validation groups/scenarios, and consistent invalid-payload/error-response shape. | Symfony `form-validator-designer`; the validation-architecture portion of Laravel/PHP Core's `api-designer`. |
| `admin-panel` | A back-office/admin-panel package is wired (e.g. an Eloquent-CRUD admin generator, an EasyAdmin/Sonata-style bundle, or similar) for internal/staff-facing CRUD. | Building/extending admin-panel resources: CRUD forms and tables bound to the real domain models, relation managers, custom actions/widgets - scoped explicitly to internal tooling, not customer-facing UI. | Laravel `filament`. |
| `api-platform-design` | A declarative, metadata-driven API resource framework is wired (e.g. API Platform or a similar attribute/annotation-driven REST layer). | Designing declarative API resources: operation/metadata configuration, input/output DTOs, providers/processors that delegate to real services/repositories, and per-operation security expressions. **Scope vs. `api-designer` (`php-frameworks.md`):** when this framework is the target's primary/sole API mechanism, `api-platform-design` owns ALL resource-level design and `api-designer` narrows to any remaining hand-rolled endpoints only (stating so explicitly) rather than both re-deriving the same route/contract guidance. | Symfony `api-platform-designer`. |
| `console-commands` | The target ships custom CLI commands (beyond the framework's own built-ins) for operational or batch tasks. | Implementing CLI commands: input/argument validation, delegating business logic to a service (never inlining it in the command), safe progress/output streaming, and correct exit codes. | Symfony `console-command-coder`; the command-authoring half of Laravel `console-scheduler`. |
| `repository-review` | A repository/data-access layer sits between domain code and persistence (ORM repositories, custom query classes, or a Doctrine/PDO repository pattern). | Auditing data-access code: parameter binding safety, business-readable method names, index/sort alignment, bounded/stable pagination, N+1 risk, and keeping repositories free of authorization/formatting/side-effect logic. | Symfony `repository-reviewer`. |
| `container-review` | Dependency injection is configured declaratively (a container config file such as `services.yaml`/`services.php`, autowiring, compiler passes), not purely via code-driven bindings. | Reviewing DI wiring for correctness: autowiring/alias/tag configuration, decorator ordering, compiler-pass effects, and verifying actual wiring with the framework's own container-debug tooling where available. | Symfony `container-reviewer`. |
| `test-data-factories` | Deterministic test-data helpers exist or are needed (model factories, fixture classes, object-mother builders). | Building realistic, overrideable, non-random-by-default test-data factories/fixtures, with no assertions embedded in factory code. | Laravel's factory conventions (folded into `eloquent`/`test-generator`); Symfony `fixture-factory-generator`. |
| `package-authoring` | The target itself is a distributable Composer package/library (a reusable dependency, not a deployed application) - e.g. no deployment target in section 5, a library-shaped `composer.json` `type`, and consumers expected to `require` it. | Package-authoring concerns: public API stability, Service-Provider/Bundle-style integration points for the consuming app, publishable config/migrations/views, and package-local testing (e.g. Orchestra Testbench or an equivalent harness). | Laravel `package-developer`. |

## Generation Rule

For each row above whose signal in profile section 3.1 is `confirmed`/`inferred` **present** (the pattern itself was found), generate exactly one skill named per the "Generic skill name" column (or a close, evidence-fitting variant, e.g. `eloquent-patterns` instead of `orm-patterns` when Eloquent specifically is confirmed - keep it descriptive of the real tool). Ground the body in the target's real package/class names from the scan, never in the framework example named in "Generalizes" unless that IS the target's actual framework. A confidence tag on a line does NOT by itself mean "generate this skill" - a line can be `confirmed`/`inferred` **absent** (e.g. "Repository/data-access layer: inferred none", "DI container configuration style: code-driven bindings only (confirmed)" when the row requires declarative config, "Package vs. application: deployed application (confirmed)" when the row requires a distributable package) - those are confirmed/inferred findings of *absence* and MUST be skipped exactly like `unknown`/bare `none`. Only generate for a signal whose confirmed/inferred finding is that the pattern is actually present.

Every selected specialty also needs evidence for concrete target usage, not package presence alone. Apply the contracts below independently.

Before compiling a specialty contract:

- Treat every “What it guides”/procedure concern as a review candidate, not a confirmed target capability. Keep unsupported items as questions or external requirements; do not assert deduplication, retention, locking, tenant scope, failure handling, audit, or similar behavior without a bounded target anchor.
- Consume the target's real test topology and exact/resolved command definitions. Verification must select an applicable suite/focused command or a concrete manual assertion with expected results.
- Map each intersecting high-priority invariant ID to a specialty procedure step and verification assertion; preserve explicit failure-state and forbidden-state expectations.
- Carry path authority and every material adjacent owner into ownership/routing. Include positive, negative, ambiguous, and cross-domain routing cases rather than choosing one generic sibling.

## Enforceable Contracts

### `orm-patterns`
- **Evidence/trigger:** ORM package plus real mappings/models and non-trivial query/relationship usage. Owns application use of an already-designed schema; excludes schema/migration design.
- **Procedure:** inspect mappings and exemplar queries; define association/cast/hydration rules; review lifecycle hooks and mass assignment; choose bounded loading/batching; preserve transactions.
- **Verify/output/failure:** run mapped-query and integration tests plus query-count checks where available; output usage guidance/findings and commands. Stop when schema intent is unknown.
- **Sibling/example:** defer schema to `database-designer`, rollout to `migration-safety`. Good: cite an actual aggregate query. Bad: generic CRUD snippets.

### `migration-safety`
- **Evidence/trigger:** migration tool, real history, and a pending/non-trivial schema rollout. Owns deployment safety; excludes schema intent.
- **Procedure:** classify lock/data/compatibility risk; design expand-backfill-contract phases; define online index/batching; coordinate old/new code compatibility; state rollback limits.
- **Verify/output/failure:** dry-run/status, representative data checks, and post-deploy invariants; output rollout/rollback/checkpoints. Block destructive steps without data/backup/approval evidence.
- **Sibling/example:** `database-designer` chooses the schema; `release` executes deployment. Bad: a single irreversible rename.

### `async-jobs`
- **Evidence/trigger:** real producer, handler, and configured transport/scheduler. Owns message/job reliability; excludes broker provisioning.
- **Procedure:** define payload/version/identity; place dispatch relative to transaction; enforce idempotency; configure retries/backoff/failure transport; handle ordering/concurrency; instrument correlation.
- **Verify/output/failure:** handler tests and duplicate/retry/failure-path tests; output contract, retry policy, operational checks. Stop when delivery semantics are unknown.
- **Sibling/example:** integration skill owns provider transport. Bad: “queue it for performance.”

### `event-boundary-review`
- **Evidence/trigger:** actual event classes and listeners/subscribers/observers. Owns event boundaries and thin adapters; excludes notification-channel design.
- **Procedure:** map publisher/event/listeners; verify event facts and timing; identify hidden workflow/side effects; move orchestration to services; assess transaction/replay behavior.
- **Verify/output/failure:** listener tests and event-contract checks; output boundary findings/refactor plan. Flag unknown ordering instead of assuming it.
- **Sibling/example:** `async-jobs` owns async reliability; domain review owns invariants. Bad: business workflow embedded in listeners.

### `notification-delivery`
- **Evidence/trigger:** concrete multi-channel notification classes and routing. Owns channel choice, templates, deduplication, and delivery failure; excludes generic mail-provider setup.
- **Procedure:** map event/recipient/channel; enforce preference/permission rules; design stable notification identity; render per-channel content; queue/retry safely; process bounce/failure.
- **Verify/output/failure:** rendering, routing, duplicate, and failure tests; output channel matrix and delivery contract. Stop if recipient authority is unknown.
- **Sibling/example:** email/SMS integration owns transport credentials/webhooks. Bad: send every event on every channel.

### `caching-strategy`
- **Evidence/trigger:** real cache-aside/tag/model/query usage and write paths. Owns cache correctness; excludes broad performance diagnosis.
- **Procedure:** identify source of truth; define keys/tags/tenant scope; set freshness; map every write to invalidation; prevent stampede; define bypass/degradation.
- **Verify/output/failure:** stale-read, concurrent miss, invalidation, and outage tests; output cache contract/key map. Disable/bypass rather than serve unbounded stale data when correctness is uncertain.
- **Sibling/example:** `performance` measures hot paths. Bad: “cache for 60 minutes.”

### `file-storage`
- **Evidence/trigger:** configured disk/adapter plus upload/download code. Owns secure file lifecycle; excludes provider account provisioning.
- **Procedure:** classify files/visibility; validate names/type/size by content; stream; isolate tenant paths; issue bounded signed URLs; define retention/deletion and malware path if evidenced.
- **Verify/output/failure:** unauthorized access, oversized/type spoof, streaming, and expiry tests; output storage/access contract. Fail closed on validation/authorization.
- **Sibling/example:** object-storage integration owns SDK/service failures. Bad: trust extension and make uploads public.

### `auth-scaffolding`
- **Evidence/trigger:** real guard/firewall/session setup and policy/gate/voter enforcement. Owns local authentication/authorization scaffolding; excludes external identity protocol lifecycle.
- **Procedure:** map principals/guards; inspect login/session lifecycle; define policy subjects/actions; enforce at every entry point; test allow/deny/abstain and ownership.
- **Verify/output/failure:** auth/session/policy tests and route coverage; output enforcement map. Deny on ambiguous principal or missing policy.
- **Sibling/example:** identity integration owns tokens/OAuth; `security-review` threat-reviews changes. Bad: controller-only role checks.

### `form-validation-design`
- **Evidence/trigger:** dedicated request/form/DTO validators and custom constraints/groups. Owns validation architecture and error shape; excludes domain invariants that cannot be validated at the boundary.
- **Procedure:** classify syntactic/context/domain rules; choose DTO/form and groups; design reusable constraints; normalize errors; avoid database races masquerading as validation.
- **Verify/output/failure:** valid/invalid/group/localization tests; output validation map and error contract. Stop when rule authority is unknown.
- **Sibling/example:** `api-designer` owns endpoint contract. Bad: duplicate inconsistent inline rules.

### `admin-panel`
- **Evidence/trigger:** wired admin package and actual internal resources. Owns staff CRUD/actions/widgets; excludes customer UI and domain-rule bypass.
- **Procedure:** map resource to model/service; scope queries and permissions; configure forms/tables/relations; route actions through domain services; audit sensitive actions.
- **Verify/output/failure:** role/tenant/action tests and browser checks; output resource/action design. Fail closed on missing staff authorization.
- **Sibling/example:** frontend skills own customer UI; domain review owns business transitions. Bad: direct status edits in generic CRUD.

### `api-platform-design`
- **Evidence/trigger:** wired declarative resource framework and real resource metadata. Owns resources/operations/providers/processors/security; excludes remaining hand-rolled endpoints.
- **Procedure:** define resource identity/operations; separate input/output DTOs; delegate provider/processor; scope serialization; encode per-operation security; document filters/errors.
- **Verify/output/failure:** metadata/schema and operation security tests; output resource contract. Stop on ambiguous ownership/serialization exposure.
- **Sibling/example:** `api-designer` owns only hand-rolled endpoints. Bad: duplicate controller and resource operation.

### `console-commands`
- **Evidence/trigger:** actual custom command classes and command conventions. Owns command interface/adaptation; excludes business logic and scheduling reliability.
- **Procedure:** define arguments/options/exit codes; validate input; delegate service; stream bounded progress; support safe dry-run/idempotency when required; handle interruption/errors.
- **Verify/output/failure:** command tester cases for success/input/failure; output CLI contract. Never swallow failure with exit code zero.
- **Sibling/example:** `async-jobs` owns scheduled async work. Bad: domain transactions inside execute().

### `repository-review`
- **Evidence/trigger:** custom repository/query layer with real methods. Owns data-access semantics, binding, pagination, query/index alignment; excludes authorization and formatting.
- **Procedure:** trace callers/contracts; inspect binding and tenant predicates; compare filters/sorts to indexes; bound result sets; detect N+1; keep side effects out.
- **Verify/output/failure:** integration/query-plan/query-count checks; output concrete findings. Escalate missing tenant/ownership context.
- **Sibling/example:** `orm-patterns` owns broader ORM usage; `database-designer` owns indexes/schema. Bad: “repositories should be generic CRUD.”

### `container-review`
- **Evidence/trigger:** declarative container files/autowiring/tags/decorators and framework debug tooling. Owns effective DI wiring; excludes code-driven factory design.
- **Procedure:** map interface aliases/services/tags; inspect visibility/autowiring; verify decorators/order; account for environment overrides/compiler passes; inspect effective container.
- **Verify/output/failure:** lint/debug-container commands and boot tests; output wiring findings. Do not infer runtime wiring from one config fragment.
- **Sibling/example:** `architecture-implementer` adds feature wiring. Bad: checklist with no effective-container inspection.

### `test-data-factories`
- **Evidence/trigger:** existing factories/fixtures/builders and repeated test-data setup. Owns deterministic composable test objects; excludes assertions and production seed data.
- **Procedure:** identify valid defaults from domain rules; make overrides explicit; model relationships/states; avoid uncontrolled randomness/time; separate persistence; provide named states.
- **Verify/output/failure:** deterministic repeated tests and invariant checks; output factory API/examples. Stop rather than invent valid domain defaults.
- **Sibling/example:** `testing` chooses scenarios. Bad: random invalid fixtures with hidden database writes.

### `package-authoring`
- **Evidence/trigger:** Composer library shape plus documented consumer API/integration points. Owns public compatibility, extension/config publication, and package harness; excludes app deployment.
- **Procedure:** identify supported PHP/framework matrix; classify public API; design provider/bundle hooks; isolate optional integrations; test installed-consumer behavior; plan deprecations/versioning.
- **Verify/output/failure:** lowest/highest dependency matrix, package validation, and consumer harness; output compatibility/release contract. Block accidental public breaks.
- **Sibling/example:** `dependency-manager` owns dependency hygiene; `release` handles package publishing only if evidenced. Bad: application-only assumptions in a library.
