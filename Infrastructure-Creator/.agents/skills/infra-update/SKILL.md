# Infra Update

## Overview

`infra-update` is the upgrade orchestrator (see `AGENTS.md`'s "Orchestration Exception"). A target generated by an older release of this generator gets the current release's improvements without losing a single local edit: the contract is the `.infra-manifest.json` that `infra-generate` wrote at the target root - the generator version, the source profile, and the sha256 of every generator-owned file at the moment of generation.

The core rule is mechanical and absolute:

- A file whose current hash **equals** its manifest hash was never touched by the target team - the generator still owns it and may replace it with the freshly generated version.
- A file whose current hash **differs** (or that was deleted) belongs to the target team now - it is NEVER overwritten; it goes into the report's "requires decision" section with three-way context.
- A file the manifest does not list is not the generator's - it is never read for diffing, never modified, never deleted, and never a verification finding (`bootstrap-verifier` skips it entirely, placeholders included).

One recorded exception refines the first rule: a file listed in the manifest's `decisions` map (see "Decision Memory" below) is user-owned by explicit choice even while its hash equals the manifest hash. There, hash equality means "unchanged since the user's decision", never "the generator may replace it".

## Decision Memory

A per-file human decision must outlive the run that recorded it. Re-hashing a kept file into the new manifest is NOT enough: on the next run its hash would equal the manifest hash and the core rule would classify it as generator-owned, silently overwriting the very edit the user chose to keep. The manifest therefore carries an optional top-level `decisions` map:

```json
"decisions": {
  ".claude/hooks/local-context.sh": {
    "decision": "kept",
    "rejected_sha256": "<sha256 of the staged version the user declined>",
    "task": "TASK-007"
  }
}
```

- **Who writes it:** only `infra-update` (step 8). A fresh `infra-generate` manifest has no `decisions` - nothing has been decided yet.
- **`decision`** is `kept` (the user kept the target version) or `merged` (the user hand-merged); both mean the file stays user-owned regardless of hash equality. **`rejected_sha256`** is the sha256 of the staged version the user was shown when deciding (for `merged`, the staged version the merge was built from).
- **Effect on classification (step 5):** for a file with a `decisions` entry whose target hash equals its manifest hash:
  - staged sha256 == `rejected_sha256` -> the generator's output has not changed since the decision: keep the target version automatically, report it as "standing decision honored", and carry the entry forward unchanged;
  - staged sha256 != `rejected_sha256` -> the generator now produces content the user has never evaluated: **requires decision** again.
  A `decisions` entry NEVER authorizes an automatic replace - its only automatic outcome is keeping the target version.
- **Lifecycle:** choosing "take staged version" in a later run deletes the entry (the file is generator-owned again); choosing keep or merge writes/refreshes the entry with that run's staged sha256; an entry whose path is no longer listed in `files` is dropped.

## Generated File Naming Convention (MANDATORY)

Allocate a new `tasks/TASK-{N}/` for the update run. Staging output goes to `tasks/TASK-{N}/infra-update-staging/` (inside this generator's workspace, never inside the target). The run report is `tasks/TASK-{N}/infra-update-report.md`. Writes into the target happen only in step 7, only per the classification rules.

## Process

1. **Read the manifest.** Require the target project path. Load `<target>/.infra-manifest.json`. If it is missing or unparsable, **ABORT without writing anything** and tell the user why: the target is a legacy generation (produced by a generator release before manifests existed, v1.3.x or earlier) or the manifest was deleted. Recovery options to present: (a) re-run `infra-generate` and take the collision guard's explicit overwrite/merge decision, or (b) if - and only if - the user can vouch that the generated files were never edited, hand-build a manifest with the recipe in `infra-generate`'s "Version Stamp & Generation Manifest" section and re-run `infra-update`. Never fabricate a manifest yourself from the target's current state without that explicit user confirmation - hashing user-edited files as if freshly generated would authorize overwriting their edits.
2. **Re-validate the profile.** The manifest names its source profile (`tasks/TASK-{N}/infra-scan-project-profile.md`). Re-check its cited evidence against the target's current files exactly as `infra-generate` step 2 does. If the profile is missing or the target has drifted materially (framework change, new/removed integrations, edition selection no longer true), stop and recommend a fresh `infra-scan` - an update run must not generate from stale evidence.
3. **Compare versions.** Read this generator's root `VERSION` file and the manifest's `generator_version`; summarize the relevant `CHANGELOG.md` entries between them for the user. Equal versions are allowed (the run degrades to a drift-repair pass) but say so explicitly.
4. **Regenerate into staging.** Fan out the same forges `infra-generate` uses (`policy-forge`, `skill-forge`, `hook-forge`, `memory-seed`, then `agent-forge`, `command-forge`, `skill-flow-composer`) with the same profile and edition selection, but with every write redirected into `tasks/TASK-{N}/infra-update-staging/` laid out exactly like the target root. **Exception - memory state:** skip chunk seeding, `INDEX.md`, and `.memory-counter` entirely (the target's memory is live data); stage only the generator-owned memory surface (`memory-bank/scripts/`, `memory-bank/templates/`, `memory-bank/README.md`, and the `project-brain/` skeleton files the manifest tracks).
5. **Classify every file** by comparing three sets - manifest entries, staged files, current target files (sha256 each):
   | Manifest | Staged | Target state | Classification |
   | --- | --- | --- | --- |
   | listed | staged | hash == manifest, no `decisions` entry | **Safe update**: replace with staged version (no-op when staged == target). |
   | listed | staged | hash == manifest, `decisions` entry present | **Standing decision**: keep target automatically when staged sha256 == `rejected_sha256`; otherwise **requires decision** (see "Decision Memory"). Never auto-replace. |
   | listed | staged | hash != manifest, or file deleted | **Requires decision** - never auto-applied. |
   | listed | not staged | hash == manifest | **Obsolete**: the current generator no longer produces it; offer removal, decided by the human. |
   | listed | not staged | hash != manifest | **Requires decision** (user-adopted file the generator would drop). |
   | not listed | staged | absent from target | **New file**: write it, add to the manifest. |
   | not listed | staged | present in target | **Requires decision** - a user file collides with a new generator file; never overwrite. |
   | not listed | not staged | anything | **User file: untouchable.** Not read, not diffed, not reported. |
6. **Present decisions.** For every "requires decision" file give three-way context: (a) *as generated* - the manifest hash plus, when the target is a git repo, the originally generated content recovered from history (`git log --diff-filter=A --format=%H -- <file>` or the commit matching the manifest's `generated_at`); state honestly when the original content is unrecoverable and only its hash remains; (b) *as the current generator would write it* - the staged version; (c) *as it is in the target* - the current content. Offer per-file choices: keep target version / take staged version / manual merge. Proceed only on explicit answers; an unanswered file keeps the target version and stays listed in the report. Record each outcome for step 8: keep and merge become (or refresh) `decisions` entries; take-staged removes any existing entry.
7. **Apply.** Write safe updates, new files, approved decisions, and approved removals into the target. Re-stamp the first line of the target's `AGENTS.md` with the current version/task/date (per `infra-generate`'s stamp format) - if `AGENTS.md` itself was user-modified and the user chose to keep their version, update only the stamp line and record that in the report.
8. **Rewrite the manifest.** Rebuild the `files` map with the current `VERSION`, this update run's task id, and the same editions - via the full recipe from `infra-generate`'s SKILL.md for `mode: full` manifests; for `mode: merge` manifests, re-hash only the previous manifest's surviving entries plus the files this run actually wrote (never a full tree walk - the target's pre-existing files must stay untracked forever). Preserve the manifest's `mode`. Then write the `decisions` map per "Decision Memory": every keep/merge decision from step 6 - and every carried-forward standing decision - gets an entry with this run's staged sha256 as `rejected_sha256`; every take-staged decision removes its entry; entries for paths no longer in `files` are dropped. Re-hashing a kept file alone does NOT protect it: without its `decisions` entry the next run would see hash == manifest and auto-replace it.
9. **Verify.** Run `bootstrap-verifier` against the updated target (it validates the refreshed manifest too). A failure means the update is not done. Verification sees only generator-owned (manifest-tracked) files: anything the team added under the edition roots since generation - their own skills, hooks, notes - is untouchable and can never fail the gate, in either manifest mode.
10. **Report.** Write `tasks/TASK-{N}/infra-update-report.md`: version from -> to, the full classification table, every decision taken (or still pending), and the verification result.

- [n] new files added

| --- | --- | --- |

## Guardrails

- MUST ABORT before any write when `.infra-manifest.json` is missing or unreadable, with the legacy-target explanation and recovery options - never guess ownership of files.
- MUST NOT overwrite, merge into, or delete any file whose current hash differs from its manifest record - or any manifest-listed file that was deleted - without an explicit per-file human decision.
- MUST NOT auto-replace a file carrying a manifest `decisions` entry - hash equality there records a standing human decision, not generator ownership; the only automatic outcome for such a file is keeping the target version (when the staged sha256 still equals its `rejected_sha256`).
- MUST persist every keep/merge decision into the manifest's `decisions` map in step 8, and MUST drop an entry only on an explicit take-staged decision (or when its path leaves the manifest entirely).
- MUST preserve the manifest's `mode`, and for `mode: merge` targets MUST NOT re-run the full tree-walking recipe - only previously tracked files plus files this run actually wrote may be (re-)hashed; the team's pre-existing files stay untracked.
- MUST NOT read, modify, or delete files absent from the manifest, except writing a genuinely new generator file into a path that does not exist in the target.
- MUST NOT touch memory state ever: `memory-bank/chunks/`, `memory-bank/INDEX.md`, `memory-bank/.memory-counter`, `memory-bank/local/`, `project-brain/indexes/`, and Project Brain record/state directories are the target team's live data and stay out of staging, the manifest, and the diff entirely.
- MUST NOT change the edition selection during an update - adding or removing an edition is an `infra-generate` run with its collision guard, not an update.
- MUST rewrite `.infra-manifest.json` (full recipe, current `VERSION`) and pass `bootstrap-verifier` before reporting success.
- MUST keep staging inside this generator's own `tasks/TASK-{N}/` - the target sees only final, decided writes.

## Final Output

Return the version transition, counts per classification (auto-applied / decisions with outcomes / untouched), any pending decisions the user still owes, the refreshed manifest summary, the verification result, and the report path.
