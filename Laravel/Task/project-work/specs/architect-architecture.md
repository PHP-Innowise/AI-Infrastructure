# Design: PracticePerfect platform architecture (Laravel)

White-label, multi-tenant coaching platform. Four roles, eight epics, 419
acceptance criteria, 58 tables. This document settles layering, module
placement, authorization, tenancy, sync-versus-queued work, branding delivery
and the deployment shape. It does not design endpoints (`api-designer`),
screens (`frontend-design`) or migrations beyond their ordering
(`database-designer-schema.md` already holds the schema).

**Framework: Laravel.** Every mechanism below is named in Laravel terms —
Eloquent, global scopes, model events, Policies and Gates, middleware, Form
Requests, Queues, Artisan, service providers, Blade. Two of this document's
inputs (`specs/database-designer-schema.md`,
`specs/council-sharelink-tenant-resolution.md`) were written during a Symfony
edition of the same product and are marked *translate* in
`specs/MANIFEST.md:53-54`. Their **product decisions are honoured verbatim**;
their **mechanisms are re-expressed**, and a translation table is given under
"Tenancy enforcement" so a reader can map citations in those files onto the
mechanisms here.

**Two invariants the boundary rule exists to protect** (carried from
`council-sharelink-tenant-resolution.md:158, 322-328`):

1. `Identity` is the sole creator of memberships. `Scheduling` (RSVP-sourced
   association), `Forms` (camp conversion) and `Identity`'s own ShareLink flows
   all call `MembershipService`; none writes `PlayerTrainerMembership` or
   `CoachMembership` directly. BR-03-1 (`epic-03:302`) fixes the three
   association sources; A3 (`open-questions.md:33`) adds `camp_registration`
   as a fourth.
2. A module may write another module's models **only** through the owning
   module's service. `PublicTenantCodeRegistry`, `TokenLedger` and
   `MembershipService` are the three that matter.

### Where the code lives

```
app/
  Platform/       Models/  Tenancy/  Services/  Http/  Policies/
  Identity/       Models/  Actions/  Services/  Http/  Policies/  Jobs/
  Scheduling/     …
  Crm/  Content/  Billing/  Growth/  Administration/  Forms/
  Support/        framework-wide glue only
bootstrap/providers.php      one provider per module
routes/  web.php  public.php  console.php     (public.php = the code-resolved group)
database/migrations/         one ordered timeline, M0…M7 (see "Build order")
resources/views/{module}/    plus resources/views/public/ for code-resolved pages
```

PSR-4 stays `"App\\": "app/"`, so a class is `App\Identity\Models\Account`. No
package-per-module, no `nwidart/laravel-modules` — the directories are a
convention, and the boundary is enforced by test, not by autoloader tricks:

```php
arch('Platform depends on nothing')
    ->expect('App\Platform')
    ->not->toUse(['App\Identity','App\Scheduling','App\Crm','App\Content',
                  'App\Billing','App\Growth','App\Administration','App\Forms']);
```

That single Pest arch test is the cheapest possible check on the whole module
map, and it is why `PublicTenantCode.reference_id` carries no foreign key
(`database-designer-schema.md:418-430`): a real FK from a `Platform` table into
`Identity`'s `share_link` or `Forms`' `form` would make the bottom of the stack
depend upward, and the test would catch it.

## Layering

```
Route  →  Middleware  →  Form Request  →  Controller  →  Action/Service  →  Eloquent
                                              ↓                ↓
                                          Policy/Gate      Job (queued)
```

| Layer | Responsibility | Never |
|---|---|---|
| Route file | URL, name, middleware, `defaults('tenant_source', …)` | Contain logic |
| Middleware | Session, auth, **tenant resolution**, feature gate, rate limit | Business rules |
| Form Request | Field validation; `authorize()` delegates to a Policy | Re-state a business rule the Action owns |
| Controller | Translate HTTP to one Action call and one response | Query Eloquent; touch Stripe; send mail |
| Action / Service | One cohesive workflow; owns its `DB::transaction` boundary | Return a `Response`; know about HTTP |
| Eloquent model | Persistence, casts, relations, tenancy trait | Authorize; send mail; call another module |
| Job | Slow, retryable or fan-out work, under a re-established tenant | Hold a business rule that a synchronous caller depends on |

**Actions over fat services.** One class per use case
(`Identity\Actions\AcceptShareLink`, `Billing\Actions\SpendTokens`,
`Scheduling\Actions\CreateRsvp`), invoked as `__invoke` or `handle`. A
"service" name is reserved for the few genuinely stateful collaborators the
carried-over documents already name by role — `MembershipService`,
`TokenLedger`, `CrossTenantReadService`, `PublicTenantCodeRegistry`,
`FeatureGate`, `StripeReportingReader`, `AuditLogger`.

**No repository layer.** Eloquent query scopes plus a handful of dedicated
query classes for the read-heavy dashboards (Epic-03 Quick View, Epic-07
metrics) cover it. A repository wrapper over Eloquent buys nothing here and
would hide the global scope that is doing the tenancy work.

**Layering exceptions, stated once:**

- **Code-resolved public routes run without a user, or with one whose session
  context is a different trainer.** They resolve the tenant from the code in
  the route (source 5 below). This covers Epic-08's form routes (BR-08-6,
  `epic-08:203`) and Epic-01's ShareLink acceptance routes (BR-01-14/15,
  `epic-01:280-281`). The allow-list is declared on the routes themselves.
  — carried from `council-sharelink-tenant-resolution.md:434-441`.
- **Stripe webhooks** run without a user and without a session; the tenant is
  resolved from the `PaymentRecord` the event references, after the receipt row
  is written.
- **Artisan commands** start with *no* tenant and must enter one explicitly.

## Tenancy enforcement

### The threat, stated plainly

A tenancy leak in this product discloses, to the wrong trainer: a minor's
medical restriction and injury status, and their scholarship / financial-aid
status — flags 3, 4, 5 and 6 of the eight system flags (`epic-03:352`) — along
with the parent's contact details and the child's attendance history. BR-01-9
(`epic-01:275`), BR-03-2 (`epic-03:303`) and BR-05-17 (`epic-05:267`) each
state isolation independently. A6 (`open-questions.md:36`) refused a
cross-trainer parent view *specifically* because "tenancy isolation is the
highest-risk defect class in this product". This is the defect class the whole
design is arranged around.

### The layers

Numbering is kept identical to the carried-over documents so their citations
resolve. Layer 0 is not in their numbering; it is the precondition all the
others read.

The middle column below is a **lookup key, not an instruction** — it exists so
that a reader following a citation into `database-designer-schema.md`
("architecture Layers 1-4", lines 619-620) or
`council-sharelink-tenant-resolution.md` ("all five layers", line 288) lands on
the right row. It is the only place in this document where a mechanism from the
other framework is named, and nothing is to be built from it.

| # | Layer | Lookup key: mechanism named in the carried-over docs | **Laravel mechanism — build this** |
|---|---|---|---|
| 0 | Resolved tenant, mandatory | `TenantContext` | `App\Platform\Tenancy\TenantContext`, a `scoped()` container binding whose `trainerId()` **throws** |
| 1 | The column | `trainer_id` denormalized, never joined | identical — `$table->foreignId('trainer_id')->constrained()` |
| 2 | Automatic scope | Doctrine SQL filter | Eloquent **global scope** (reads) + **`creating` model event** (writes) |
| 3 | Post-load assertion | `postLoad` listener | **`retrieved` model event** assertion |
| 4 | Database enforcement | PostgreSQL RLS, `USING` + `WITH CHECK` | identical |
| 5 | Authorization | Voter | **Policy / Gate** |

Each layer catches what the one above it cannot:

- **1 without 2** is just a column.
- **2 without 3** misses rows that arrived through a builder the scope never
  saw (`withoutGlobalScope`, eager-load constraints, `Model::unguarded`).
- **2 and 3 without 4** miss every `DB::table()` call, every `DB::select()`,
  every raw expression, and every model that forgot the trait. This is the
  single most important reason RLS is non-negotiable in Laravel specifically:
  **global scopes are an Eloquent feature, not a connection feature.** The
  query builder is one `DB::` away at all times.
- **4 without 0** is the failure mode with no symptom: if `current_setting`
  returns a stale or absent value the policy still evaluates, it just
  evaluates against the wrong tenant or none. Hence the sentinel and the gate.
- **5** is orthogonal: resolution is not authorization (see below).

### Layer 0 — `TenantContext`

```php
namespace App\Platform\Tenancy;

final class TenantContext
{
    private ?int $trainerId = null;

    public function trainerId(): int
    {
        return $this->trainerId
            ?? throw new TenantNotResolved();   // never null, never "all"
    }

    public function isResolved(): bool { return $this->trainerId !== null; }

    public function set(int $trainerId): void
    {
        $this->trainerId = $trainerId;
        $this->pushToDatabase((string) $trainerId);
    }

    public function forget(): void
    {
        $this->trainerId = null;
        $this->pushToDatabase('0');             // sentinel — matches no real row
    }

    /** @template T */
    public function runFor(int $trainerId, \Closure $callback): mixed
    {
        $previous = $this->trainerId;
        $this->set($trainerId);
        try { return $callback(); }
        finally { $previous === null ? $this->forget() : $this->set($previous); }
    }

    private function pushToDatabase(string $value): void
    {
        DB::selectOne("select set_config('app.current_trainer_id', ?, false)", [$value]);
    }
}
```

Four things in that snippet are decisions, not style:

1. **`trainerId()` throws.** Returning `null` and letting a scope degrade to
   "no `where` clause" is how a tenancy bug becomes a disclosure instead of an
   error. `TenantNotResolved` renders as a 500 in production and is asserted by
   test.
2. **Sentinel `'0'`, not `NULL`.** `current_setting('app.current_trainer_id')`
   on an unset variable raises `SQLSTATE 42704`, which is technically
   fail-closed but produces an unreadable error on every unscoped query. `'0'`
   matches no row because identity columns start at 1
   (`database-designer-schema.md:1861`), so an unresolved query returns empty
   from the database *and* has already thrown at layer 0.
3. **`set_config(..., false)`, not `SET`.** `false` = session-scoped (the `SET`
   equivalent), which is required because not every unit of work runs inside a
   transaction (`database-designer-schema.md:1864-1867`); `true` would be `SET
   LOCAL` and would silently lose the tenant the moment a write happened
   outside a transaction. `set_config` is used rather than `SET` because it is
   a function call and therefore **parameterizable** — `SET app.x = ?` is not,
   and would force string interpolation of a value into SQL.
4. **`scoped()`, not `singleton()`.** `$this->app->scoped(TenantContext::class)`
   resets the instance between queued jobs and (if Octane is ever adopted)
   between requests. Under php-fpm the two are identical; `scoped()` is the one
   that stays correct if the runtime changes.

### Layer 1-3 — the `BelongsToTenant` trait

Every model backing a table on `config/tenancy/trainer_scoped_tables.txt` uses
it. The list is the 38 tables at `database-designer-schema.md:1944-1984`.

```php
trait BelongsToTenant
{
    public static function bootBelongsToTenant(): void
    {
        static::addGlobalScope(new TenantScope);                      // L2 read

        static::creating(function (Model $m) {                        // L2 write
            $m->trainer_id ??= app(TenantContext::class)->trainerId();
        });

        static::saving(function (Model $m) {                          // L2 write
            if ($m->exists && $m->isDirty('trainer_id')) {
                throw new TenantReassignmentAttempted($m);
            }
        });

        static::retrieved(function (Model $m) {                       // L3
            if ((int) $m->trainer_id !== app(TenantContext::class)->trainerId()) {
                throw new TenantMismatch($m);   // a row got here another way
            }
        });
    }
}
```

`TenantScope` is a one-line `Illuminate\Database\Eloquent\Scope` adding
`where("{$model->getTable()}.trainer_id", $context->trainerId())` — table-qualified,
because unqualified it breaks the moment a join is added.

`trainer_id` is in `$guarded` on every such model and is never in `$fillable`.
The `creating` hook is the only writer.

**The honest gap, and why it is survivable.** `withoutGlobalScope(TenantScope::class)`
is public Eloquent API; anyone can call it. So is `DB::table('rsvp')`. Neither
is stopped by layers 2 or 3. Both are stopped by layer 4 — RLS applies to the
connection, so the worst outcome is *sees nothing*, not *sees another
trainer's roster*. On top of that, an arch test forbids both outside the
tenancy namespace:

```php
arch()->expect('App')->not->toUse('withoutGlobalScope')
    ->ignoring('App\Platform\Tenancy');
```

### Layer 4 — Row-Level Security

Unchanged from `database-designer-schema.md:1869-1913`; restated because it is
the layer with no Laravel involvement at all and must not be diluted in
translation.

```sql
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON <table>
    USING      (trainer_id = current_setting('app.current_trainer_id')::bigint)
    WITH CHECK (trainer_id = current_setting('app.current_trainer_id')::bigint);
```

**Both clauses, always.** `USING` alone isolates reads and leaves `INSERT`
completely unconstrained — a trainer could write a row into another tenant and
then never be able to see it, which is the worst of both worlds. The startup
gate asserts `pg_policies.with_check IS NOT NULL` for exactly this reason.

`FORCE ROW LEVEL SECURITY` is deliberately never set, so the owner role can
migrate and backfill without fighting its own policies.

In Laravel these statements live in the migration that creates the table, as
`DB::statement(...)` after the `Schema::create(...)` block — same file, same
transaction, so a table can never exist without its policy.

**The publication exception** (`database-designer-schema.md:1885-1913`) is the
one declared widening: `playlist` and `content_item` widen **reads** on "has
ever been published" (`ever_published_at IS NOT NULL`), because BR-04-4/BR-04-5
(`epic-04:460-469`) require other trainers to discover public content and
require existing references to keep working after a revert to private. Writes
stay strictly tenant-owned via four separate policies (`SELECT` widened;
`INSERT`/`UPDATE`/`DELETE` not). The corresponding Eloquent scope on those two
models is `PublishedOrOwnedScope`, not `TenantScope` — a different class, so
the widening is visible in the model rather than hidden in a condition.

### Layer 5 — Policies

See "Authorization" below. Stated here only to close the sequence:
**resolution is not authorization** (`council-sharelink-tenant-resolution.md:409-412`).
A resolved tenant makes trainer-scoped tables *reachable*. Whether this actor
may do anything inside that tenant is still a Policy decision on the row.

### Resolution sources, in order

Exactly one component resolves the tenant: `App\Platform\Http\Middleware\ResolveTenant`.
Nothing else ever calls `TenantContext::set()` — except `runFor()`, which is
its own audited/explicit entry point for jobs and commands.

1. **Super Admin, not impersonating** → no tenant. The context stays
   unresolved and the sentinel stands. Super Admin screens read through
   `CrossTenantReadService`, never through tenant-scoped models.
2. **An active impersonation session** → the impersonated account's tenant.
   Read from the global `impersonation_session` partial index
   (`database-designer-schema.md:506-510`); the 1-hour expiry is evaluated at
   read time, not by a job (BR-01-22, `epic-01:288`).
3. **The player's or coach's selected trainer context** — held in the session,
   or supplied by the request on a route whose purpose is to change or target
   it — validated in either case against the global `account_trainer_link`. An
   unvalidated candidate resolves nothing.
   *(Carried verbatim from `council-sharelink-tenant-resolution.md:378-381`.
   The widening from "session only" exists because AC-01-17/AC-01-23 let a
   parent whose session context is trainer A add a child to trainer C. The
   security-bearing half — validation against `account_trainer_link` — is
   unchanged.)*
4. **A Trainer or Coach account with exactly one membership** → that trainer.
   BR-01-11 (`epic-01:277`) makes this total for coaches: a coach is active
   under exactly one trainer, so a coach never sees a switcher.
5. **A public code carried in the route**, on routes explicitly allow-listed as
   code-resolved: Epic-08's form shareable code, and an `Identity` ShareLink
   code on the `/join/{code}` and `/invite/{code}` route group. The code is
   looked up in the global `public_tenant_code` mapping, which holds the code,
   the owning trainer, and an opaque `(kind, reference_id)` pair — nothing
   else. Like `account_trainer_link`, this mapping is global because the
   resolver runs before a tenant does, and it is read for no purpose other than
   resolution. The allow-list is declared as route data in one place so the
   surface is enumerable.
   *(Carried from `council-sharelink-tenant-resolution.md:390-398`.)*

**Precedence.** Sources 1 and 2 outrank everything. On an allow-listed
code-resolved route, **source 5 outranks sources 3 and 4**: the tenant is the
code's trainer, never the session's selected context and never a trainer named
in the submitted payload. Elsewhere, 3 then 4.

Without this precedence, an existing player accepting a second trainer's
ShareLink resolves to the trainer already in their session, and the membership
`INSERT` is rejected by the RLS `WITH CHECK` with `SQLSTATE 42501` — on the
platform's most common signup path (BR-01-14, `epic-01:280`; BR-03-1,
`epic-03:302`). This is the failure the council was convened over.

### The circularity, and the two global tables

**To learn which trainer a ShareLink belongs to, you must read `ShareLink`. To
read `ShareLink`, you must already have that trainer as the tenant.**
(`council-sharelink-tenant-resolution.md:102-103`.)

That single fact makes a tenancy-exempt `code → trainer` lookup **the
precondition for every option, not one option among several**. Two tables are
therefore global and carry **no RLS policy, ever**:

| Table | Why it must be global | Written by |
|---|---|---|
| `account_trainer_link` | The resolver's own source for sources 3 and 4 — read before a tenant exists (`database-designer-schema.md:355-380`) | `MembershipService`, in the same transaction as the membership row it mirrors |
| `public_tenant_code` | The resolver's source for source 5 — `code`, `trainer_id`, `kind`, `reference_id`, and nothing else (`database-designer-schema.md:382-446`) | `PublicTenantCodeRegistry` only, called by `Identity` on ShareLink creation and by `Forms` on form publication, in the same transaction |

`config/tenancy/resolver_global_tables.txt` lists exactly these two, and the
startup gate asserts `relrowsecurity = false` on both. A policy accidentally
added to either would fail **every login and every public code-resolved route**
in the fail-closed-silence shape this architecture is most afraid of
(`database-designer-schema.md:1991-2006`).

The mapping carries no expiry, status or use count. Those stay on the
trainer-scoped `share_link` / `form` rows, so the mapping can never drift into
an authority: a stale mapping row grants a tenant and nothing else.

### The allow-list, as Laravel route data

```php
Route::middleware('throttle:public-code')
     ->defaults('tenant_source', 'public_code')
     ->group(function () {
         Route::get ('/join/{code}',            [JoinController::class, 'show'])->name('public.join.show');
         Route::post('/join/{code}/register',   [JoinController::class, 'register'])->name('public.join.register');
         Route::post('/join/{code}/associate',  [JoinController::class, 'associate'])->name('public.join.associate');
         Route::get ('/invite/{code}',          [InviteController::class, 'show'])->name('public.invite.show');
         Route::post('/invite/{code}/register', [InviteController::class, 'register'])->name('public.invite.register');
         Route::get ('/f/{code}',               [PublicFormController::class, 'show'])->name('public.form.show');
         Route::post('/f/{code}',               [PublicFormController::class, 'submit'])->name('public.form.submit');
         Route::get ('/f/{code}/confirmation',  [PublicFormController::class, 'confirmation'])->name('public.form.confirmation');
         Route::post('/f/{code}/convert',       [PublicFormController::class, 'convert'])->name('public.form.convert');
     });
```

Route `defaults()` is chosen over a route middleware because it is **data on
the route, inspectable from the router** — which is what makes the allow-list
testable rather than merely documented:

```php
it('has exactly nine code-resolved routes', function () {
    $actual = collect(Route::getRoutes())
        ->filter(fn ($r) => ($r->defaults['tenant_source'] ?? null) === 'public_code')
        ->map->getName()->sort()->values()->all();

    expect($actual)->toBe([/* the nine names, literally */]);
});
```

Growing the allow-list therefore requires editing a test — a reviewed act.
That test is the cheapest early check on the single largest security boundary
in this design (`council-sharelink-tenant-resolution.md:476-479`).

`/livewire/update` is **not** and must never be on this list — see
"Presentation".

### Failure modes

Carried from `council-sharelink-tenant-resolution.md:285-294`, unchanged in
substance.

| Situation | Behaviour |
|---|---|
| Code absent from `public_tenant_code` (forged, scanned) | No tenant → **404**, indistinguishable from any unknown URL. **Zero** trainer-scoped statements issued. Rate-limited; counted, not audited |
| Code maps to a trainer but the `ShareLink` is inactive / expired / exhausted | Tenant **is** resolved (harmless). The trainer-scoped row loads under all layers; `ShareLinkPolicy::resolve()` denies → "this invitation has expired" with the resend path (AC-01-42, BR-01-15 `epic-01:281`). No membership. **Audited** |
| Mapping row survives a deleted `ShareLink` | Tenant resolves; no row under that tenant; same expired page. Benign by construction |
| Logged-in child clicks a link | Tenant resolves; the AC-01-31 branch runs (tell the child to ask a parent, email the parent — `epic-01:335`); `MembershipService` is not called |
| Coach already active under another trainer | Tenant resolves; `CoachMembership` creation refused by `Identity`'s own rule (BR-01-11, `epic-01:277`; `epic-01:329`) — a domain refusal, not a tenancy one |
| Payload names a trainer other than the code's | **Impossible by construction** — the trainer is never read from the payload on these routes |
| Existing player, session context A, accepts trainer B's code | Source 5 outranks source 3 → tenant is **B**. The `WITH CHECK` violation cannot occur |

**What is audited**: the membership created under a code-resolved tenant, and
the stale-link denial. **Not** the unknown code — auditing an anonymous,
scannable route makes the audit log the amplification target
(`council-sharelink-tenant-resolution.md:279`). Unknown codes are rate-limited
and counted.

### Tenancy in queued jobs

A worker process is long-lived and reuses its database connection across jobs.
`app.current_trainer_id` therefore survives from one job into the next unless
something clears it. That is the leak.

**Automatic, not opt-in.** An `InteractsWithTenant` trait a developer must
remember is a convention, and this document's position on conventions is the
same as the schema's on ledger immutability: it survives exactly until someone
forgets. So the tenant rides on **every** payload and is established by a
listener:

```php
// PlatformServiceProvider::boot()
Queue::createPayloadUsing(fn () => [
    'trainer_id' => app(TenantContext::class)->isResolved()
        ? app(TenantContext::class)->trainerId()
        : null,
]);

Queue::before(function (JobProcessing $e) {
    $trainerId = $e->job->payload()['trainer_id'] ?? null;
    $agnostic  = in_array(TenantAgnostic::class, class_implements($e->job->resolveName()) ?: []);

    match (true) {
        $trainerId !== null => app(TenantContext::class)->set($trainerId),
        $agnostic           => app(TenantContext::class)->forget(),
        default             => throw new TenantNotResolved(),   // fail closed
    };
});

Queue::after(fn () => app(TenantContext::class)->forget());
Queue::failing(fn () => app(TenantContext::class)->forget());
Queue::exceptionOccurred(fn () => app(TenantContext::class)->forget());
```

- A job dispatched inside a tenant carries it; the worker re-establishes it
  before `handle()` and clears it after, on **all four** exit paths.
- A job dispatched with no tenant runs only if it declares
  `implements TenantAgnostic` — Stripe webhook ingest, platform-wide
  reconciliation, mail to a Super Admin. Anything else throws rather than
  running tenant-less.
- The reset target is the sentinel, so a leak degrades to "sees nothing".
- Workers run with `--max-time=3600 --max-jobs=1000` so connections recycle on
  a bounded schedule regardless.

**Fan-out keeps one tenant per job.** Trainer-cancels-event refunds (BR-02-12,
`epic-02:323`) dispatch one job per RSVP, each taking only the token-balance
lock, exactly as the carried-over lock-ordering decision requires
(`database-designer-schema.md:2044-2048`).

### Tenancy in Artisan commands

Commands start with **no** tenant:

```php
Artisan::starting(fn () => app(TenantContext::class)->forget());
```

so the first trainer-scoped query in a careless command throws instead of
returning something. A command that needs a tenant takes `--trainer=` and wraps
its work in `TenantContext::runFor()`. A command that spans tenants (ledger
reconciliation, the pending-payment sweep) lists trainer ids on the crossing
connection and then loops `runFor()` — one resolved tenant at a time, never a
crossing write.

`php artisan migrate` is the deliberate exception: it runs on the **owner**
connection, which is exempt from policy because `FORCE ROW LEVEL SECURITY` is
never set. `migrate` is the only command permitted to use that connection.

### The three database roles, and the gate

| Role | Grants | Used by |
|---|---|---|
| `pp_owner` | DDL. Exempt from policy (as table owner) | `php artisan migrate --database=pgsql_owner` only |
| `pp_app` | `SELECT/INSERT/UPDATE/DELETE`. **`NOBYPASSRLS`**, no `CREATE` on `public` | The running application, the queue worker, every command except `migrate` |
| `pp_crossing` | **`SELECT` only**, `BYPASSRLS` | `CrossTenantReadService` alone |

Three Laravel connections in `config/database.php`: `pgsql` (default,
`pp_app`), `pgsql_owner`, `pgsql_crossing`. `CrossTenantReadService` is the
only class permitted to name the third — enforced by arch test.

**The startup gate** — `php artisan tenancy:verify --strict`, run by the
php-fpm container entrypoint *before* fpm starts, and again in CI. A non-zero
exit means the container does not start. This exists because the most dangerous
RLS failure raises nothing by itself: policies that are present, correct, and
simply never consulted.

| Gate | Assertion | Query |
|---|---|---|
| 1 | The app is **not** connected as an owner or `BYPASSRLS` role | `select rolbypassrls, rolsuper from pg_roles where rolname = current_user` → both false; and `current_user = 'pp_app'` |
| 2 | Every table in `trainer_scoped_tables.txt` exists, has `relrowsecurity`, and has a policy with **both** `qual` and `with_check` | `pg_class.relrowsecurity`, `pg_policies` |
| 3 | Every table in `resolver_global_tables.txt` has `relrowsecurity = false` | same |
| 4 | `pp_app` holds no `UPDATE`/`DELETE` on `token_entry` or `audit_log_entry` | `has_table_privilege('pp_app', 'token_entry', 'UPDATE')` → false |
| 5 | No persistent connections and no transaction-mode pooler between app and PostgreSQL | `PDO::ATTR_PERSISTENT` is false; `DB_HOST` resolves to the postgres service directly |

Gate 5 is not paranoia: the whole model rests on a **session** variable. A
transaction-mode pooler hands the same backend to different tenants between
statements and breaks isolation without any error
(`council-sharelink-tenant-resolution.md:501-503`).

Gate 2's manifest is also cross-checked from the application side: a test
asserts that the set of models using `BelongsToTenant` and the set of tables in
`trainer_scoped_tables.txt` are the same set, in both directions. A table can
then neither gain RLS without a model nor gain a model without RLS.

## Authorization

### No role hierarchy

Four roles, fixed constants, per A2 (`open-questions.md:32`) and BR-01-7
(`epic-01:273`):

```php
enum Role: string { case SuperAdmin = 'super_admin'; case Trainer = 'trainer';
                    case Coach = 'coach'; case Player = 'player'; }
```

A backed enum on `account.role`, cast on the model. **No `spatie/laravel-permission`**,
no roles table, no permissions table — A2 puts the User Role Editor out of MVP,
which makes roles constants rather than data, and a permission package's whole
value proposition is that they are data.

**And no hierarchy, expressed concretely: `Gate::before` is never registered.**
The tempting line is:

```php
Gate::before(fn ($user) => $user->role === Role::SuperAdmin ? true : null);  // NEVER
```

It is exactly the defect the brief names: an ownership check like
`$playerNote->trainer_id === $context->trainerId()` silently returns *true* for
a Super Admin who holds no tenant at all — because the check never runs. Every
Super Admin capability is instead an explicit ability on an explicit policy
(`AdministrationPolicy@viewPlatformDashboard`, `@impersonate`, `@toggleFeature`),
and Super Admin action *inside* a tenant happens by impersonation (source 2,
which resolves a real tenant and writes an `impersonation_session` row) or
through `CrossTenantReadService` (SELECT-only, audited). A test asserts no
`before` callback is registered on the gate, and a second asserts a Super Admin
with no resolved tenant is **denied** an ownership ability.

### Where authorization lives

| Question | Mechanism |
|---|---|
| May this actor act on **this row**? | **Policy**, auto-discovered as `App\{Module}\Policies\{Model}Policy`. Ownership compares against `TenantContext::trainerId()`, not against `$user->trainer_id` — the resolved tenant is the authority |
| May this actor use this **capability** at all? | **Gate** (`Gate::define('feature:lppp', …)`), backed by `FeatureGate` reading `feature_toggle`; BR-07-1/2/3 (`epic-07:364-379`) |
| May this **request shape** proceed? | **Form Request** `authorize()`, delegating to the Policy — never re-implementing it |
| Coarse route gating | `->middleware('can:…')` and `->middleware('role:trainer')` |
| In Blade | `@can`, `@cannot` |
| Guest-allowed abilities (public form, ShareLink) | Policy methods typed `?Account $user` — Laravel invokes them for unauthenticated actors when the parameter is nullable. `FormSubmissionPolicy::create(?Account $user, Form $form)` and `ShareLinkPolicy::resolve(?Account $user, ShareLink $link)` are the two |

**Feature toggles are a Gate, not a tenancy concern.** `feature_toggle` is
global with a `trainer_id` *reference* and no RLS
(`database-designer-schema.md:539-557`); all three rows are seeded enabled at
trainer creation so `FeatureGate` never has to treat "no row" as a third state.
BR-07-3 requires the effect within seconds and requires disabling to hide, not
delete — so the gate is evaluated per request against the row, never cached
beyond the request.

### The authorization rules that are genuinely non-obvious

| Rule | Source | Mechanism |
|---|---|---|
| A coach may edit attendance only on the day of the event; trainer and Super Admin at any time | BR-02-18 (`epic-02:329`) | `AttendanceRecordPolicy@update` — a time comparison in the policy, not a scheduled lock |
| A note's author may edit for 24h; a trainer cannot edit a coach's note ever | BR-03-12 (`epic-03:319`) | `PlayerNotePolicy@update` |
| Only the assigned coach may mark attendance, and only after start | BR-02-16 (`epic-02:327`) | `AttendanceRecordPolicy@create` |
| Private events are invisible, not merely forbidden | BR-02-6 (`epic-02:317`) | Query scope for the list; policy for the direct link → 403 "Access Denied" |
| Coaches cannot touch forms at all | BR-08-20 (`epic-08:217`) | `FormPolicy` denies `coach` on every ability |
| Super Admin sees all forms **via impersonation** | BR-08-21 (`epic-08:218`) | Follows automatically: impersonation is source 2, so the normal `FormPolicy` applies inside a real tenant |
| Child spend needs parent approval; parent may opt a child out for tokens only | BR-01-18/19 (`epic-01:284-285`) | Not a policy — a workflow state (`child_approval_request`). The policy asks "is there an approval for this request"; the 48h expiry is read-time, not a job |

## Synchronous and asynchronous work

The rule: **if an invariant depends on it, it is synchronous and inside the
transaction; if it is slow, external, or fan-out, it is queued.** Deferring an
invariant to a queue turns a constraint into a suggestion.

### Synchronous, inside one `DB::transaction`

| Work | Why it cannot be deferred |
|---|---|
| RSVP create: capacity lock + eligibility + token spend or payment intent | Capacity is `SELECT … FOR UPDATE` + `COUNT(*)` (`database-designer-schema.md:123-131`). BR-02-7 (`epic-02:318`) forbids over-capacity RSVP; a queued check races |
| Camp submission: capacity + duplicate-email | BR-08-7/BR-08-10 (`epic-08:204,207`); Epic-08 names the atomic DB-level check explicitly (`epic-08:272`) |
| Token spend, refund, grant; balance projection update | The ledger invariants (below) span two tables and must commit together |
| Coupon redemption | BR-06-10 one-per-transaction (`epic-06:230`); the usage-limit check must hold the coupon row |
| Membership creation + the `account_trainer_link` mirror | A dual write the resolver depends on (`database-designer-schema.md:374-380`) |
| ShareLink / Form creation + the `public_tenant_code` mapping | Same transaction, or the code exists with no tenant mapping |
| Stripe webhook **receipt row** | Inserted in its own transaction *before* the body is parsed; the unique violation on `stripe_event_id` **is** the duplicate detection (`database-designer-schema.md:594-613`) |

### Queued (`database` driver, `queue:work`)

| Work | Queue | Notes |
|---|---|---|
| All mail — welcome, verification, reset, invitation, RSVP confirmation, approval request/decision, auto-denial notice | `mail` | Q-01.04 default (`open-questions.md:181`). `Mailable` + `->queue()` |
| Stripe webhook **processing** (after the receipt row) | `payments` | Retries with backoff, 3 attempts / 24h (BR-05, `epic-05:330`) |
| Trainer-cancels-event refund fan-out | `payments` | One job per RSVP; each takes only the balance lock (BR-02-12, `epic-02:323`) |
| Stripe Connect onboarding-status refresh | `payments` | |
| Logo image processing on branding upload | `default` | ≤2MB, PNG/JPG/SVG; validation is synchronous, derivative work is not |
| Bulk playlist assignment to a label group | `default` | BR-04-13 (`epic-04:523`) — one assignment can target N players |
| Referral reward grant on referee's first purchase | `default` | BR-06-5 (`epic-06:223`); it is a ledger write, so the job calls `TokenLedger`, which is synchronous *within* the job |

Queue connection is `database`, so a job dispatched inside a request commits
with the request's transaction when dispatched via `dispatch()->afterCommit()`
— which is the default this project sets (`config/queue.php` →
`'after_commit' => true`). A job that observes a row the transaction has not
committed is a bug class this removes wholesale.

### Scheduled (`schedule:work` in the queue container)

| Task | Cadence | Source |
|---|---|---|
| Auto-denial **notification** for 48h-old pending approvals | every 15 min | BR-01-18 (`epic-01:284`) |
| Auto-cancel RSVPs whose payment has not cleared in 7 days | hourly | BR-05-9 (`epic-05:253`) |
| Stripe webhook retry sweep (`processed_at IS NULL`) | every 5 min | `database-designer-schema.md:612-613` |
| Token ledger reconciliation (invariant I1) | nightly | `database-designer-schema.md:2019` |
| Coupon auto-deactivation on usage limit | not scheduled | Derived at read time; the limit is checked under the row lock at redemption (`epic-06:288`) |

### Time-based state is derived at read time, never flipped by a job

This is a carried-over decision with three named instances and it is worth
stating as a rule, because getting it wrong produces a state column that is
wrong for up to one scheduler interval:

- A 48-hour-old approval request is expired **because its timestamp says so**,
  not because a job ran. `child_approval_request.status` deliberately has no
  `expired` value (`database-designer-schema.md:811-818`).
- An impersonation session is over after 1 hour by the same reasoning
  (`database-designer-schema.md:511-514`).
- A referral's "Rewarded" state is not stored at all — it is derived from
  whether a `token_entry` for it exists (`database-designer-schema.md:2411`).

The scheduler's job in each case is to send the *notification*, not to change
the *fact*.

## The token and payment ledger

`token_entry` is **append-only**. Balances are projections. Refunds are
compensating entries. Money is integer minor units.

### The seven invariants and where each is enforced

Carried unchanged from `database-designer-schema.md:2017-2025`; the
enforcement column is re-expressed in Laravel where it named a Doctrine
construct.

| # | Invariant | Enforced by |
|---|---|---|
| I1 | Balance projection = sum of that pair's entries | Not a DB constraint (spans two tables). `TokenLedger` maintains both in one transaction; `php artisan tokens:reconcile` + a test verify |
| I2 | Balance never negative | `CHECK (balance >= 0)` on `token_balance` |
| I3 | Every `spend` records the beneficiary player; every `refund` inherits it | `CHECK` requires the column on `spend`/`refund`; inheritance is `TokenLedger::refund()`, covered by a test. **A7** (`open-questions.md:37`) |
| I4 | Sum of refunds against one spend never exceeds it | Lock the spend row (`lockForUpdate()`, no write), then sum and compare inside the transaction — it cannot be a running counter, because I7 forbids `UPDATE` |
| I5 | Sign matches kind | `CHECK` on `amount` vs `kind` |
| I6 | At most one entry per (payment record, purpose) | Partial unique index `(payment_record_id, kind) WHERE payment_record_id IS NOT NULL` |
| I7 | **No entry is ever updated or deleted** | `REVOKE UPDATE, DELETE ON token_entry FROM pp_app` |

**I7 is a database privilege, not a code convention.** In Laravel the
migration that creates the table ends with
`DB::statement('REVOKE UPDATE, DELETE ON token_entry FROM pp_app');` and the
same for `audit_log_entry` (BR-07-4/6, `epic-07:382,390`). The Eloquent model
additionally throws in `updating` and `deleting` — but that is for the error
message, not for the guarantee. A trait with no setters survives exactly until
someone adds a setter; a revoked privilege does not.

### Lock ordering

**Fixed order: token balance row first, then the event row.** Made structural
by funnelling every dual-lock path through two methods that can only be called
in that order (`database-designer-schema.md:2027-2048`):

```php
TokenLedger::lockBalance(int $trainerId, int $parentAccountId): TokenBalance   // always first
EventCapacity::lockEvent(int $eventId): Event                                  // only from inside
                                                                               // a transaction that
                                                                               // already holds the balance
```

Both a paid RSVP and an RSVP-cancellation refund traverse them in that order. A
concurrency test drives both against the same parent and event and asserts no
deadlock. Trainer-initiated cancellation never holds both at once: it commits
the event cancel first, then fans out one refund job per RSVP, each taking only
the balance lock.

### Money and the platform fee

```php
$feeMinorUnits = intdiv($amountMinorUnits * $feeRateBasisPoints + 5000, 10000);
```

Round half up, integer arithmetic only, no float anywhere near a money figure.
Verified against both worked examples in the epic: $100 at 500 bps → exactly
$5.00 (BR-05-7, `epic-05:251`); $20 at 500 bps → exactly $1.00 (AC-05-11)
(`database-designer-schema.md:2059-2085`).

Computed **once**, at `payment_record` creation, from
`trainer_billing_settings.platform_fee_basis_points` read at that moment and
snapshotted onto the payment record. A rate read live at display time would
retroactively rewrite every historical figure; AC-05-27 requires new rates to
apply to new transactions only.

**The trainer absorbs the fee** — it is included in the listed price, per the
settled fee call (`open-questions.md:43`) and BR-05-7. The player is never
charged more than the listed amount.

**The earnings boundary.** No revenue, payout or net-earnings figure is stored
or summed locally. `platform_fee_minor_units` is stored because it is an
*input* to the Stripe Connect charge (`application_fee_amount`), not an output
presented as revenue. Stripe's own processing fee is never mirrored.
`StripeReportingReader` is the only source of any earnings figure shown to a
trainer, read live, never cached (`database-designer-schema.md:2098-2109`).

In Eloquent: a `MoneyCast` (`CastsAttributes`) maps every `*_minor_units`
column to an `int`-backed `Money` value object. An arch test forbids `(float)`
and `floatval` in `App\Billing`.

## White-label branding as a runtime value

**Branding is a value resolved per request from the resolved tenant. It is
never compiled, never cached, and never a build artifact.** AC-01-62 requires
changes to apply immediately (`database-designer-schema.md:350`), which forbids
config caching, per-trainer CSS bundles and any warm cache keyed by anything
but the request.

| Piece | Mechanism |
|---|---|
| Source of truth | `trainer_branding_settings` — `logo_path`, `primary_color_hex`; global table, public by nature because it renders on unauthenticated camp forms (BR-08-6, `epic-08:203`; `database-designer-schema.md:340-353`) |
| Which trainer's brand | **The resolved tenant, always.** There is no second answer, which is what makes this simple: the public camp form is branded because source 5 already resolved its tenant |
| Fallback | No tenant (Super Admin, platform pages) → platform default, `Task/designs/default_logo.svg` |
| Binding | A `Branding` readonly value object, `scoped()` in the container, hydrated from `TenantContext` |
| Delivery to the view | `View::composer('layouts.*', BrandingComposer::class)` → `$branding` |
| Delivery to CSS | A `<x-branding-style />` Blade component emitting **CSS custom properties** into `<head>` |
| Tailwind wiring | `theme.extend.colors.brand` references the custom properties, so utility classes (`bg-brand`, `text-brand-deep`) work without a per-tenant build |
| Logo | `<img src>` from `Storage::disk('public')` — never inlined (`database-designer-schema.md:348`). Upload validated ≤2MB, PNG/JPG/SVG |

```blade
{{-- resources/views/components/branding-style.blade.php --}}
<style>
  :root {
    --brand-primary:      {{ $branding->primaryHex }};
    --brand-primary-soft: color-mix(in srgb, {{ $branding->primaryHex }} 80%, white);
    --brand-primary-deep: color-mix(in srgb, {{ $branding->primaryHex }} 80%, black);
    --brand-primary-rgb:  {{ $branding->primaryRgb }};
  }
</style>
```

The four property names are the contract in `Task/designs/DESIGN_TOKENS.md:40-46`.
The soft/deep shades are derived **in the browser** with `color-mix()` rather
than server-side, so there is no palette-generation step, nothing to cache and
nothing to invalidate — the design tokens file describes `lightenColor` /
`darkenColor` helpers (lines 34-38), and `color-mix()` is the same
transformation with no code.

`primary_color_hex` is `CHAR(7)` with a `CHECK` for `^#[0-9A-Fa-f]{6}$`, so the
value interpolated into that `<style>` block cannot be anything but a hex
colour. The Blade escape stays regardless.

## Presentation

**Blade everywhere. Livewire 3 permitted only on authenticated, session-resolved
screens. Livewire is forbidden on code-resolved public routes.**

The reason is specific and structural: Livewire component updates POST to a
single shared endpoint, `/livewire/update`. That route carries **none** of the
original route's parameters — so it cannot be on the source-5 allow-list, and
its tenant necessarily resolves from session context (source 3). On an
authenticated trainer screen that is correct. On `/f/{code}` it is wrong or
absent, and the failure would be silent-ish and confusing.

Epic-08's own UX assumptions make the constraint free: forms are one page, not
multi-step, and completion is expected under five minutes (`epic-08:259-260`).
Plain Blade with a form POST is sufficient.

Where Livewire earns its place: the CRM segmentation panel (BR-03-13's
AND-combined filters, `epic-03:322`), the event builder, the playlist builder,
the Super Admin dashboards.

Structural check: a test asserting no view under `resources/views/public/**`
references a Livewire component, and that no route with
`tenant_source=public_code` renders one.

**Inertia + Vue is rejected**: it introduces an SPA boundary, a second
serialization surface for tenant-scoped data, and a JSON API this MVP has no
requirement for. Nothing in the eight epics asks for client-side routing.

## Deployment shape

Docker Compose only. **No host PHP, Composer, Node, or PostgreSQL.** Every
command a developer runs is `docker compose exec …`.

```
compose.yaml
  web        nginx:alpine            → serves public/, proxies *.php to php:9000
  php        ./docker/php            → php:8.4-fpm-alpine + pdo_pgsql, intl, gd, zip, opcache
                                       Composer lives IN the image
                                       entrypoint: artisan tenancy:verify --strict → php-fpm
  postgres   postgres:17-alpine      → initdb/00-roles.sh creates pp_owner/pp_app/pp_crossing
                                       volume: pgdata
  queue      same image as php       → supervisord: queue:work + schedule:work
  mail       axllent/mailpit         → SMTP 1025, UI 8025
```

**The php image is multi-stage.** Stage 1 is `node:22-alpine` running
`npm ci && npm run build`; stage 2 copies `public/build` into the PHP runtime
image. That is what keeps Node off the host without adding a permanent Node
service. An optional `vite` service running `npm run dev` may be enabled for
development; it is not part of the running stack.

**Role bootstrapping** — `docker/postgres/initdb/00-roles.sh`, run once on an
empty data directory:

```sh
pp_owner     CREATEDB, owns the schema, runs migrations
pp_app       LOGIN NOBYPASSRLS;  REVOKE CREATE ON SCHEMA public FROM pp_app
pp_crossing  LOGIN BYPASSRLS;    GRANT SELECT only
ALTER DEFAULT PRIVILEGES FOR ROLE pp_owner IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO pp_app;
ALTER DEFAULT PRIVILEGES FOR ROLE pp_owner IN SCHEMA public
    GRANT SELECT ON TABLES TO pp_crossing;
```

The `ALTER DEFAULT PRIVILEGES` lines are what make every future table grant
correctly without a per-migration grant statement — and they are why the two
append-only tables must **`REVOKE`** in their own migration rather than
selectively granting (`database-designer-schema.md:1919-1936`).

**`DB_USERNAME=pp_app`** in `.env`. `pgsql_owner` and `pgsql_crossing` take
their credentials from separate env vars and are used by exactly one caller
each. There is no configuration in which the application's default connection
is anything but `pp_app` — Gate 1 refuses to start otherwise.

Health checks: `pg_isready` on postgres; `php -v` on php; `web` and `queue`
both `depends_on: { php: { condition: service_healthy } }`. `queue` also waits
on postgres, because the `database` queue driver needs the `jobs` table.

**Framework tables carry no RLS and must be excluded from the manifest**:
`migrations`, `jobs`, `job_batches`, `failed_jobs`, `sessions`, `cache`,
`cache_locks`, `password_reset_tokens`. They are infrastructure keyed by their
own identifiers, not by trainer. Gate 2 iterates the manifest, not the
information schema, so their absence is correct rather than merely tolerated —
but the model↔manifest test (above) is what keeps the manifest honest.

Epic-05, then wire the paywall.

Migrations are **one ordered timeline** in `database/migrations`, following the
carried-over M0-M7 grouping (`database-designer-schema.md:2253-2364`).
Timestamps encode the order; the module a migration belongs to is in its
filename (`2026_01_02_000300_create_share_link_table.php`). A single timeline
is chosen over per-module migration paths because foreign-key order across
modules is real (`child_approval_request` needs `rsvp`, `token_package` and
`playlist` to exist — `database-designer-schema.md:819-822`) and Laravel offers
no ordering guarantee across registered paths.

| Group | Contents | Notes |
|---|---|---|
| M0 | Extensions, framework tables (`sessions`, `cache`, `jobs`, …) | No RLS, not on the manifest |
| M1 | Identity + Platform core — **the walking skeleton**, incl. `account_trainer_link` and `public_tenant_code` | Nothing works until the resolver's two sources exist |
| M2 | Scheduling | |
| M3 | Crm + Content (parallel, per A10) | |
| M4 | Billing — incl. the `REVOKE` on `token_entry` | |
| M5 | Growth | |
| M6 | Administration — incl. the `REVOKE` on `audit_log_entry` | |
| M7 | Forms | |

Each migration that creates a trainer-scoped table does three things in one
file: `Schema::create`, `ENABLE ROW LEVEL SECURITY` + `CREATE POLICY`, and an
append to `config/tenancy/trainer_scoped_tables.txt`. Gate 2 then fails
immediately on any migration that did only the first.

## Decisions

| Decision | Chosen | Rejected | Why the rejected option lost |
|---|---|---|---|
| Tenancy read/write scope | Eloquent **global scope** + `creating` stamp + `retrieved` assertion, in one `BelongsToTenant` trait | A `where('trainer_id', …)` per query; a base `TenantModel` class; a query-builder macro | Per-query filtering is a convention with 419 chances to be forgotten. A base class forecloses using traits Laravel expects on models (`SoftDeletes`, `HasFactory`) and still leaves `DB::table()` open — which is why the global scope is a *layer*, not the answer |
| The unresolved-tenant behaviour | `TenantContext::trainerId()` **throws** | Return `null` and let the scope emit no `where`; return `0`; return all trainers for Super Admin | Returning null is the exact shape of the disclosure this design exists to prevent: one forgotten resolution and a trainer list becomes a platform list. Returning "everything" for Super Admin bakes a hierarchy into the primitive |
| Session variable statement | `select set_config('app.current_trainer_id', ?, false)` | `DB::statement("SET app.current_trainer_id = '$id'")`; `SET LOCAL` / `set_config(…, true)` | `SET` takes no bind parameters, forcing interpolation into SQL. `SET LOCAL` is transaction-scoped and loses the tenant on any write outside a transaction — and not every unit of work here runs in one |
| Where the tenant is set | **One** middleware, `ResolveTenant`; plus `TenantContext::runFor()` for jobs and commands | A scope opened inside `MembershipService` (council option B); writing `account_trainer_link` first (option A); moving membership creation into `Platform` (option C) | All three are **circular**: they must be handed the ShareLink's trainer, which can only be learned by the trainer-scoped read that has not happened yet (`council-sharelink-tenant-resolution.md:100-118`). B additionally creates a second setter of the tenant, in a service with four callers across three modules, with no role gate |
| Pre-tenant code lookup | Global `public_tenant_code` mapping (council option G), read by the resolver | Making `share_link`/`form` global (options D/E); routing the lookup through `CrossTenantReadService` (option F) | D discloses trainer A's invitation list, recipient emails and per-link analytics to trainer B behind policies alone. E dissolves tenancy on the CRM's most-read table and contradicts BR-03-2. F attaches an anonymous, scannable route to the `BYPASSRLS` connection **and** writes an audit entry per probe — audit-log amplification (`council-sharelink-tenant-resolution.md:330-356`) |
| Allow-list declaration | Route `defaults('tenant_source','public_code')`, asserted by test against `Route::getRoutes()` | A route middleware alias; an `if` on the path prefix inside the middleware; a config array | A middleware alias is not readable back off the route as data in a form that makes the *complete set* assertable. A path-prefix `if` is not enumerable at all. The allow-list is the whole security boundary; it has to be greppable and testable |
| Tenant on queued jobs | `Queue::createPayloadUsing` + `Queue::before/after/failing/exceptionOccurred`, automatic for every job; `TenantAgnostic` marker required to opt out | An `InteractsWithTenant` trait each job must use; re-resolving from the job's own model | An opt-in trait is a convention that survives until someone forgets — and the failure is a long-lived worker inheriting the previous job's tenant. Re-resolving from a model requires reading a trainer-scoped row without a tenant: the same circularity as the ShareLink case |
| Role model | A PHP backed enum on `account.role`; no hierarchy; **no `Gate::before`** | `spatie/laravel-permission`; a `Gate::before` Super-Admin bypass; a role-implies-role map | A2 puts the User Role Editor out of MVP, making roles constants — the package's entire value is that they are data. `Gate::before` makes every ownership check silently pass for a Super Admin holding **no tenant**, which is precisely the check that guards disclosure |
| Impersonation | First-party: `impersonation_session` row + session key + tenant re-resolution via source 2 | `lab404/laravel-impersonate` | It has no audit row, does not re-resolve a tenant (so the impersonator would keep their own, i.e. none), and does not implement BR-01-21's Super-Admin-cannot-impersonate-Super-Admin rule (`epic-01:287`) |
| Authentication | Laravel session guard, Breeze Blade scaffold | Sanctum / Passport / JWT; Fortify + a custom UI; Jetstream | No API consumer, no mobile app and no third-party client appears in any of the eight epics. A token guard would add a second authentication surface that the tenancy middleware would also have to cover. Jetstream ships team management — a *different* multi-tenancy model that would fight this one |
| Payments integration | `stripe/stripe-php` directly, behind `Billing` services | Laravel Cashier | Cashier models a first-party SaaS subscription against the app's own Stripe account. This platform is a **Connect marketplace**: money moves to the trainer's connected account with an `application_fee_amount`, and Cashier does not model that. The trainer's own $15/mo platform subscription (BR-05-13) is the one place Cashier would fit, and adopting it for one relationship would mean two payment abstractions |
| Queue driver | `database` | Redis + Horizon; `sync`; SQS | Redis is a fifth service with its own durability story, for a job volume the epics never size. `database` keeps enqueue transactional with the write that triggered it (`after_commit`). Horizon becomes available the day Redis is justified — the trigger is measured worker backlog, not preference |
| Cache and session driver | `database` | Redis; `file` | Same reason. `file` sessions do not survive a second php-fpm container and would break the moment the stack scales horizontally |
| Persistence style | Eloquent + Actions; no repository layer | A repository interface per aggregate | A repository over Eloquent hides the global scope that is performing tenancy — which is the opposite of what this design needs. The read-heavy dashboards get dedicated query classes instead, which is the same benefit without the indirection |
| Module layout | Directories under `app/`, one service provider each, boundaries enforced by Pest arch tests | `nwidart/laravel-modules`; separate Composer packages; flat `app/Models` | A package boundary for nine modules in one deployable adds build machinery for a boundary a test already enforces. Flat `app/Models` with 58 models is unnavigable and gives the module map no home |
| Presentation | Blade; Livewire only on authenticated screens | Inertia + Vue; Livewire everywhere; Blade only | Inertia adds an SPA boundary and a second tenant-scoped serialization surface for a requirement no epic states. Livewire everywhere puts a session-resolved shared endpoint (`/livewire/update`) behind pages whose tenant must come from a route code |
| Branding | Runtime CSS custom properties from the resolved tenant, `color-mix()` for shades | Per-trainer compiled CSS; a cached palette keyed by trainer; inline SVG logo | AC-01-62 requires immediate effect, which a build step and a cache both violate. An inlined logo would put trainer-controlled markup in the document |
| Migration layout | One timeline in `database/migrations`, M0-M7 by timestamp | Per-module migration paths | Laravel gives no ordering guarantee across registered paths, and cross-module FKs are real (`child_approval_request` → `rsvp`, `token_package`, `playlist`) |
| Startup gate | `artisan tenancy:verify --strict` in the container entrypoint, blocking | A CI-only check; a health endpoint; documentation | The failure it catches — the app connected as a `BYPASSRLS` role — raises **nothing** at runtime. A check that does not prevent the process from starting does not prevent the disclosure |
| Migrations connection | A separate `pgsql_owner` connection used only by `migrate` | Granting the app role `CREATE`; running migrations as a superuser | Granting `CREATE` to `pp_app` would let application code create a table without a policy — the exact hole Gate 2 exists to close |

## Risks, and the cheapest early check for each

| # | Risk | If it happens | Cheapest early check |
|---|---|---|---|
| 1 | The app connects as an owner or `BYPASSRLS` role, so **RLS is present and never consulted** | Total, silent loss of layer 4. Nothing raises | Gate 1: `select rolbypassrls, rolsuper from pg_roles where rolname = current_user` at container start; fail the boot |
| 2 | A new table ships without a policy | That table has three layers, not five, and `DB::table()` reaches it freely | Gate 2 against `trainer_scoped_tables.txt` + the bidirectional model↔manifest test |
| 3 | A policy written with `USING` but no `WITH CHECK` | Reads isolated, **writes unconstrained** — rows land in the wrong tenant and become invisible | Gate 2 asserts `pg_policies.with_check IS NOT NULL` on every standard policy |
| 4 | RLS accidentally added to `account_trainer_link` or `public_tenant_code` | **Every login and every public code route silently fails** — the resolver reads them before a tenant exists | Gate 3 asserts `relrowsecurity = false` on exactly those two |
| 5 | Fail-closed silence: an unresolved tenant yields an empty result instead of an error | A bug looks like "no data" and is triaged as a UI issue for weeks | A test asserting a trainer-scoped query with no tenant raises `TenantNotResolved`, not an empty collection |
| 6 | A queue worker inherits the previous job's tenant | Cross-tenant writes from a background job — the hardest leak to notice | A test running a tenant-1 job then a `TenantAgnostic` job on the same worker, asserting the sentinel; reset wired on all four queue events |
| 7 | The code-resolved allow-list grows without review | Any route on it resolves a tenant from a bearer code | The router test asserting the set of `tenant_source=public_code` route names against a literal list |
| 8 | `share_link`/`form` and `public_tenant_code` drift apart | A code that resolves no tenant (benign) or a mapping with nothing behind it (also benign) — but a *partial* commit is not | A test that a rolled-back ShareLink creation leaves no mapping row |
| 9 | A Livewire component reaches a code-resolved public page | `/livewire/update` resolves from session → wrong tenant or none | A test that no view under `resources/views/public/**` references a Livewire component |
| 10 | `withoutGlobalScope` / `DB::table` used in application code | Layers 2 and 3 bypassed; only RLS remains | Pest arch test forbidding both outside `App\Platform\Tenancy` |
| 11 | A `Gate::before` Super-Admin bypass is added later "for convenience" | Every ownership check silently passes for an actor with **no tenant** | A test asserting no `before` callback is registered, plus one asserting a tenant-less Super Admin is denied an ownership ability |
| 12 | Ledger drift — balance ≠ sum of entries (I1) | Money-shaped data that cannot be reconciled after the fact | `php artisan tokens:reconcile --dry-run` in CI against seeded data; nightly in production |
| 13 | Deadlock between a paid RSVP and a concurrent refund | Intermittent 500s under exactly the load that matters | A concurrency test driving both against the same parent and event, asserting no deadlock |
| 14 | A float appears near money | Rounding that is wrong by a cent and unreproducible | Unit tests on both worked examples plus the half-cent case; arch test forbidding `(float)`/`floatval` in `App\Billing` |
| 15 | A connection pooler or persistent connections enter the stack | Session variables cross tenants between statements, silently | Gate 5 asserts `PDO::ATTR_PERSISTENT` false and a direct database host; documented as a hard architectural constraint |
| 16 | Unauthenticated writes into trainer-scoped tables (`form_submission`, `share_link_open`, `player_trainer_membership`, `coach_membership`) are abused | Spam registrations and enumeration against the most public surface | Per-IP `throttle:public-code` on the whole public route group from day one; honeypot on public forms (`epic-08:271`); a counter (not an audit entry) on unknown codes |
| 17 | Epic-07 dashboard metrics are too slow live at 500 trainers / 10,000 players | AC-07-41's targets missed | Seed to target scale in CI and time the queries; only then consider a `dashboard_metrics_snapshot` table — never ahead of a measured need |

## Open questions

Genuinely unsettled. Recorded, not guessed.

1. **Where the application root lives.** The carried-over schema cites
   `Task/app/…` for compose, roles, entrypoint and the tenancy manifests
   (`database-designer-schema.md:13-25`), but `Task/` in this edition contains
   only `Epics/` and `designs/`. This document specifies the artifacts' content
   and behaviour; it does not decide whether they land in `Task/app/` (matching
   the Symfony edition's layout) or at the repository root. `Task/Epics/` is
   read-only client material, which argues against putting a live application
   underneath it. Needs a call before `architecture-implementer` runs.
2. **Player/Parent modelling.** Epic-01 states outright that it does not
   resolve it (`epic-01:302-308`). The schema adopts
   `player_profile.self_account_id` + `parent_child_link`
   (`database-designer-schema.md:2427-2434`) as its own inference. This
   architecture builds on that adoption but does not upgrade it to settled.
3. **Does a playlist purchase unlock for one child or the whole family?**
   Neither Epic-04 nor Epic-05 says. Tokens are explicitly parent-trainer
   scoped and spendable for any child (BR-05-2, `epic-05:244`); the schema
   models content access per specific player
   (`database-designer-schema.md:2436-2444`). Carried forward unresolved.
4. **Rate-limit thresholds.** BR-01-6 (`epic-01:272`) requires login rate
   limiting without naming a threshold, and the council leaves open whether the
   public-code lookup limit should match it
   (`council-sharelink-tenant-resolution.md:491-492`). This document requires
   both limiters and specifies neither number.
5. **Are Epic-07 dashboard metrics live or materialized?** The epic states both
   (`epic-07:419-425`). This architecture assumes live queries and provides no
   metrics storage; risk 17 is the trigger that would change it.
6. **Trainer timezone as the authority for time boundaries.** The 24-hour
   refund cutoff (BR-05-10, `epic-05:256`) and the one-advance-booking-per-day
   rule (BR-05-14, `epic-05:262`) both need a timezone, and no epic names one.
   The schema adds `trainer.timezone` with a default
   (`database-designer-schema.md:329`). Adopted here as the only workable
   reading; still worth the client's confirmation, because it decides whose
   midnight governs a refund.
7. **Whether Livewire is in MVP at all.** This document permits it under a
   constraint. `frontend-design` may reasonably conclude that Blade plus a
   little Alpine covers every screen, which would remove risk 9 entirely.
8. **The remaining schema open questions** — skill-level vocabulary,
   `ContentUsage` versus the Epic-04 deferral, coupon code case-sensitivity,
   `duration_seconds` nullability — stand as written at
   `database-designer-schema.md:2446-2492` and are not reopened here.
