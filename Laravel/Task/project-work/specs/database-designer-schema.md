# Design: PracticePerfect relational schema

Complete PostgreSQL 17 schema for the PracticePerfect platform, covering all
eight epics in one pass (BR-01 through BR-08, plus every acceptance criterion
that names a data field). Builds directly on `specs/architect-architecture.md`
("Entity population", "Tenancy enforcement", "The token and payment ledger")
and Section A of `specs/requirements-analyst-open-questions.md`, both settled
inputs, neither reopened here.

**This document reconciles against real scaffolding already in the repo**,
not just prose specs:

- `Task/app/compose.yaml` and `Task/app/docker/postgres/initdb/00-roles.sh` —
  the three database roles already exist: `pp_owner`, `pp_app`, `pp_crossing`.
  Names below match exactly.
- `Task/app/docker/php/docker-entrypoint.sh` (Gate 4) reads
  `Task/app/config/tenancy/trainer_scoped_tables.txt` and refuses to start if
  a table on that list lacks RLS. That file exists but is empty of table
  names. The "Row-Level Security" section below ends with the exact contents
  it should hold once migrations land.
- `Task/app/config/packages/doctrine.yaml` already sets
  `identity_generation_preferences: PostgreSQLPlatform: identity` — every
  primary key in this schema is therefore `BIGINT GENERATED BY DEFAULT AS
  IDENTITY`, not UUID. See Decisions for why that is the right call to honour
  rather than override.
- The tenancy manifest's own header comment lists "camp form submissions
  before conversion" as global. **This is wrong relative to the settled
  architecture** — `architect-architecture.md` "Entity population" places
  both `Form` and `FormSubmission` under Trainer-scoped, and the tenancy
  section's resolution source 5 ("the public form's shareable code") only
  makes sense if they are. This document follows the architecture doc (a
  settled input) over the scaffold comment (not one) and flags the
  contradiction here so whoever populates the manifest file sees it once
  clearly instead of silently.
- `specs/council-sharelink-tenant-resolution.md` — appeared in this same
  repo during this session, status "Recommendation only... nothing in
  `architect-architecture.md` is modified by this document" — so it is not
  itself a settled input this task lists, but the gap it identifies is real
  and directly bears on this schema, not just on routing: `ShareLink` and
  `Form` are both correctly trainer-scoped (RLS-protected), yet both need to
  be looked up **by code, with no tenant resolved yet**, on the platform's
  most common entry path. Under RLS's standard policy that lookup returns
  **zero rows**, silently — architecture's own "fail-closed silence" risk,
  on the one request this platform cannot afford to get wrong. The
  council's recommended fix (a minimal global `code → trainer` mapping,
  option G) is adopted below as `public_tenant_code`, because the
  alternative was shipping a schema with this gap simply undocumented. Its
  table name matches `Task/app/config/tenancy/resolver_global_tables.txt`,
  which independently confirms it exactly — that file lists
  `account_trainer_link` and `public_tenant_code` as the two tables the
  resolver reads before a tenant exists, and asserts RLS must be **absent**
  from both.

Traceability: every table cites the epic spec (file, heading, line) or the
architecture doc section it derives from. Every constraint names the rule or
query it enforces.

## Conventions

Stated once so they are not repeated 57 times below.

**Primary keys.** `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` on
every table, matching `config/packages/doctrine.yaml`'s
`identity_generation_preferences` (already scaffolded — see Decisions). Six
tables use a **shared PK/FK** (1-to-1 extension pattern) instead: their `id`
column is simultaneously the FK to the table they extend. Each is called out
where it occurs.

**Foreign keys.** Every FK column is named `<referenced_singular>_id`. Default
`ON DELETE RESTRICT` unless stated otherwise — this platform has almost no
hard deletes of referenced rows (events are Cancelled, not deleted —
AC-02-68; labels/playlists/content are soft-deleted — BR-03-5, AC-04-36) so
RESTRICT mostly documents intent rather than ever firing. `ON DELETE CASCADE`
is used only where the child row is meaningless without the parent and the
parent itself is expected to occasionally be hard-deleted (join/history rows
owned by one clear parent). Every FK column gets a btree index unless it is
already the leading column of a unique or composite index — Postgres does not
index FK columns automatically, and every join in this schema is FK-driven.

**Tenancy key (Layer 1).** Every trainer-scoped table carries
`trainer_id BIGINT NOT NULL REFERENCES trainer(id)`, denormalized directly per
architect-architecture.md "Tenancy enforcement — Layer 1", never reached by
join. It is always the first column after `id` and always indexed, usually as
the leading column of a composite index matching the table's dominant query.

**Timestamps.** `TIMESTAMPTZ`, application-assigned (Doctrine lifecycle
callbacks), not DB-generated, except where noted `DEFAULT now()` as a
backstop for rows the application always sets anyway (append-only logs).
`created_at` / `updated_at` where both apply; single-purpose names
(`joined_at`, `resolved_at`, ...) where the epic names one moment, not two.

**Money.** `INTEGER`, minor units (cents), per architect-architecture.md
"Stack" — matches Stripe's own wire format. Column names end `_minor_units`.
`INTEGER` tops out at ~$21.4M per row, far above any single amount this
platform charges (camp price cap is $1–$10,000 — AC-08-5).

**Token counts.** Plain `INTEGER`, never `_minor_units` — tokens are whole
units by design (fractional tokens are explicitly out of MVP scope,
`requirements-analyst-epic-05-payments-tokens-spec.md` "Out of MVP scope",
line 360), so there is no minor-unit concept to encode.

**Enums.** `VARCHAR` plus a `CHECK (col IN (...))`, not native `CREATE TYPE
... AS ENUM`. Rejected native enums because `ALTER TYPE ... ADD VALUE` cannot
run inside the same transaction as other DDL before PostgreSQL 12 and is
still awkward to script idempotently in a migration tool; a CHECK constraint
is a one-line migration to extend. Doctrine maps each to a PHP 8.1+ backed
enum via a custom Doctrine type (`AsEnumType` or a hand-written `Type`), so
the ORM layer still gets static typing even though the column is a plain
string underneath.

**Soft delete.** `deleted_at TIMESTAMPTZ NULL` on `playlist`, `content_item`
and `drill_detail` only, per the epic's own explicit recommendation
(`requirements-analyst-epic-04-lp-content-spec.md` AC-04-36: "soft delete —
marked deleted and hidden from the UI rather than removed from the
database"). This is what makes BR-04-12's "reference breaks and shows
Unavailable" implementable without a dangling FK: `playlist_item` and
`content_usage` keep pointing at a real row that the read layer simply
excludes and renders as unavailable, rather than at a FK target that no
longer exists.

**Capacity checks.** Nowhere in this schema is a cached "current count"
column (`current_rsvp_count`, `current_registration_count`, ...). Every
capacity check — event RSVP (AC-02-67), camp registration (Epic-08 "Risks &
Mitigations — Capacity Overselling") — is `SELECT ... FOR UPDATE` on the
capacity-holding row (`event` or `form`) followed by `COUNT(*)` of the
confirmed child rows inside the same transaction. A cached counter needs a
correct decrement on every cancellation path or it drifts silently; `COUNT(*)`
under a lock is always correct and cheap at this scale (capacity ≤ 999 rows
— BR-02-4).

**Row-Level Security.** Applies to every table in "Trainer-scoped" below and
to none in "Global". Policy SQL, the sentinel value and the three roles'
grants are collected once in "Row-Level Security", not repeated per table.

## Global tables

No `trainer_id`. Protected by role membership and voters only — see
architect-architecture.md "Entity population — Global" for why each one
cannot be trainer-scoped. Module tag shown per architect's module map.

### `account` — Platform/Identity

One row per person or Super Admin, regardless of how many trainers they are
linked to. `requirements-analyst-epic-01-user-management-spec.md` § "Data
requirements" "User" (line 310); BR-01-2, BR-01-7.

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `id` | BIGINT IDENTITY | NO | | PK |
| `email` | CITEXT | NO | | Case-insensitive per BR-01-2. Requires `CREATE EXTENSION citext` |
| `password_hash` | VARCHAR(255) | NO | | BR-01-1 |
| `role` | VARCHAR(16) | NO | | `super_admin`\|`trainer`\|`coach`\|`player` — BR-01-7, "no role hierarchy" (architect "Authorization") |
| `status` | VARCHAR(16) | NO | `'active'` | `active`\|`inactive`\|`deleted` — BR-01-23, BR-01-24 |
| `email_verified_at` | TIMESTAMPTZ | YES | NULL | Q-01.05 default: required before first login |
| `last_login_at` | TIMESTAMPTZ | YES | NULL | |
| `created_at` | TIMESTAMPTZ | NO | | |
| `updated_at` | TIMESTAMPTZ | NO | | |

- PK: `id`.
- Unique: `email`.
- Check: `role IN ('super_admin','trainer','coach','player')`; `status IN ('active','inactive','deleted')`.
- Indexes: `(role)` — Users tool role filter (AC-07-9); `(status)` — active-user counts (BR-07-7).
- GDPR deletion (BR-01-24): the application UPDATEs this row in place —
  `email` becomes `deleted_<id>@example.com` (deterministic, so the UNIQUE
  constraint can never collide), `password_hash` a random unusable value,
  `status` becomes `deleted`. Personal name/phone/photo live on
  `account_profile`, nulled in the same transaction. This is a real UPDATE,
  not a new row — `account_profile.account_id` stays valid, satisfying
  "historical records are preserved but anonymized" (BR-01-24) since every FK
  pointing at this account still resolves.

### `public_tenant_code` — Platform

**The second half of tenant resolution before a tenant exists** — where
`account_trainer_link` resolves an *authenticated* account to its trainer,
this table resolves an *anonymous, code-bearing* request to one. Added per
`specs/council-sharelink-tenant-resolution.md` "Recommendation" (option G),
which generalizes architect-architecture.md's resolution source 5 (stated
only for `Form`, silently relied on for `ShareLink` too — see the header
note above). Table name and purpose confirmed independently by
`Task/app/config/tenancy/resolver_global_tables.txt`.

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `id` | BIGINT IDENTITY | NO | | PK |
| `code` | VARCHAR(64) | NO | | The same value as the owning `share_link.code` or `form.shareable_slug` |
| `trainer_id` | BIGINT | NO | | FK → `trainer(id)` RESTRICT |
| `kind` | VARCHAR(16) | NO | | `sharelink`\|`form` |
| `reference_id` | BIGINT | NO | | **Opaque scalar, deliberately not a real FK** — see note |
| `created_at` | TIMESTAMPTZ | NO | | |

- Unique: `code` — globally, by construction (this *is* the global
  uniqueness authority now; `share_link.code`/`form.shareable_slug` staying
  separately unique on their own trainer-scoped tables is redundant but
  harmless, kept because those tables are still readable directly once a
  tenant is set).
- Check: `kind IN ('sharelink','form')`.
- Indexes: `(kind, reference_id)` — revocation lookup when a `ShareLink` is
  deactivated or a `Form` is deleted.
- **No RLS, and none must ever be added** — this table is read by
  `TenantResolver` specifically *because* no tenant is resolved yet; a
  policy here would make every login and every public code-resolved route
  silently return nothing, in exactly the fail-closed-silence shape
  architecture warns about generally (architecture "Risks — Fail-closed
  silence") and the council warns about specifically for this table. It
  belongs on `resolver_global_tables.txt`, never on
  `trainer_scoped_tables.txt`.
- **`reference_id` carries no FK on purpose.** A real FK would point at
  either `share_link(id)` or `form(id)` depending on `kind`, which is the
  same "too many possible targets for one column" shape as
  `audit_log_entry.subject_id` — except here the council's own module-map
  reasoning adds a second, sharper reason: `Platform` "may call: Nothing...
  must not depend on any other module" (architect-architecture.md, Module
  map). A real FK to an `Identity`-owned table (`share_link`) or a
  `Forms`-owned table (`form`) would make the bottom of the stack depend
  upward. `PublicTenantCodeRegistry` (below) is the single writer, and it is
  always called from the owning module (`Identity` for ShareLinks, `Forms`
  for Form), in the same transaction as the row it is registering — so the
  reference is correct by construction even without a database-level FK
  guaranteeing it.
- **Single writer**: `PublicTenantCodeRegistry::issue(code, trainer, kind,
  referenceId)` / `::revoke(code)`, a `Platform` service. `share_link`
  creation (`Identity`) and `form` publication (`Forms`) each call `issue()`
  in the same transaction that persists their own row — the boundary rule
  ("a module may write another module's entities only through the owning
  module's service") applies here exactly as it does to `TokenLedgerService`
  or `MembershipService`.
- **Resolution flow, concretely**: `TenantResolver`, on an explicit
  route allow-list (ShareLink accept/register/associate/invite routes, the
  four public form routes), reads `public_tenant_code WHERE code = :code`
  (no tenant needed — no RLS), sets the session variable to the row's
  `trainer_id`, and *then* the controller re-reads `share_link`/`form` by
  the same code — now correctly RLS-visible under the just-resolved tenant,
  with its full expiry/use-count/status detail intact. A code absent from
  this table resolves no tenant and the route 404s before any trainer-scoped
  statement is issued, matching the council's stated failure-mode table.

#### `token_entry`

- Check: `kind IN ('purchase','gift','referral_reward','refund','spend','adjustment')`;
  **sign-by-kind (I5)**: `(kind IN ('purchase','gift','referral_reward','refund') AND amount > 0)
  OR (kind = 'spend' AND amount < 0)
  OR (kind = 'adjustment' AND amount <> 0)`;
  **beneficiary required for spend/refund (I3, A7)**: `kind NOT IN ('spend','refund')
  OR beneficiary_player_id IS NOT NULL`;
  **refund must reference, others must not**: `(kind = 'refund') = (refunds_entry_id IS NOT NULL)`;
  `char_length(trim(description)) > 0`.
- Unique: **`(payment_record_id, kind) WHERE payment_record_id IS NOT NULL`**
  — this is I6, "at most one entry exists per (payment record, purpose)":
  outbound idempotency at the ledger level, so a replayed webhook cannot
  double-credit the same payment.
- Indexes: `(trainer_id, parent_account_id, created_at)` — I1's
  reconciliation query and the transaction-history screen (AC-05-23);
  `(beneficiary_player_id)`; `(refunds_entry_id) WHERE refunds_entry_id IS
  NOT NULL` — I4's lookup.
- **I3's second half** ("every refund inherits the beneficiary of the spend
  it references") is not a CHECK constraint — Postgres CHECK constraints
  cannot read another row. `TokenLedgerService::refund()` copies
  `beneficiary_player_id` from the referenced spend entry at insert time;
  a test asserts they never diverge.
- **I4** ("sum of refunds referencing one spend never exceeds that spend")
  is enforced by locking, not by a constraint, and specifically *cannot* be
  a maintained running-counter column, because I7 forbids `UPDATE` on this
  table entirely (see below) — there is no row to increment. The pattern:
  `SELECT id FROM token_entry WHERE id = :spendId FOR UPDATE` (locks the
  spend row without modifying it — a no-op `SELECT ... FOR UPDATE` is a
  legal, common serialization primitive), then a plain `SELECT
  COALESCE(SUM(amount),0) FROM token_entry WHERE refunds_entry_id =
  :spendId`, then compare against the spend's original `amount` before
  inserting the new refund — all inside one transaction. Locking the spend
  row first serializes every concurrent refund attempt against it, so the
  sum read afterward is safe even though it is a plain, unlocked read.
- **I7 (append-only) is a database privilege, not a convention.** The
  migration that creates this table runs `REVOKE UPDATE, DELETE ON
  token_entry FROM pp_app;` immediately after creation — the same pattern as
  `audit_log_entry`. `pp_app` is left with `INSERT, SELECT` only.
- **I1** (balance projection equals the sum of entries) is not a DB
  constraint at all — it cannot be, since it spans two tables. It is
  maintained transactionally by `TokenLedgerService` (insert the entry,
  update `token_balance` in the same transaction, balance row locked first
  per the fixed lock order below) and independently verified by a
  reconciliation console command plus a test, exactly as architecture
  "Invariants, as enforceable rules" specifies: "self-policing".

## Row-Level Security

Applies to every table in "Trainer-scoped" above and to none in "Global".
Three roles already exist (`Task/app/docker/postgres/initdb/00-roles.sh`):
`pp_owner` (DDL, exempt from policy, never used by the running application),
`pp_app` (the running application, subject to RLS), `pp_crossing`
(`BYPASSRLS`, `SELECT`-only, used only by `CrossTenantReadService`).

### Sentinel

`TenantContext` sets a PostgreSQL session variable on every resolution and
transition:

```sql
SET app.current_trainer_id = '<trainer.id>';   -- a resolved tenant
SET app.current_trainer_id = '0';              -- unresolved — matches no real trainer, since IDENTITY starts at 1
```

Session-scoped `SET`, not `SET LOCAL`, per architecture ("not every unit of
work runs inside an explicit transaction") — safe only because the stack
carries no persistent connections and no connection pooler, both asserted
by the container startup gate (`docker-entrypoint.sh` Gate 3).

### Standard policy

Applied to every trainer-scoped table except the three content tables:

```sql
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON <table>
    USING (trainer_id = current_setting('app.current_trainer_id')::bigint)
    WITH CHECK (trainer_id = current_setting('app.current_trainer_id')::bigint);
```

`FORCE ROW LEVEL SECURITY` is deliberately never set, so `pp_owner` can
migrate and backfill without fighting its own policies (architecture "How it
is wired").

### Widened policy — `playlist`, `content_item`

The one declared widening of tenant isolation (architecture "The publication
exception"): reads widen on "has ever been published"; writes stay strictly
tenant-owned.

```sql
ALTER TABLE playlist ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_select ON playlist
    FOR SELECT
    USING (
        trainer_id = current_setting('app.current_trainer_id')::bigint
        OR ever_published_at IS NOT NULL
    );

CREATE POLICY tenant_isolation_write ON playlist
    FOR INSERT
    WITH CHECK (trainer_id = current_setting('app.current_trainer_id')::bigint);

CREATE POLICY tenant_isolation_update ON playlist
    FOR UPDATE
    USING (trainer_id = current_setting('app.current_trainer_id')::bigint)
    WITH CHECK (trainer_id = current_setting('app.current_trainer_id')::bigint);

CREATE POLICY tenant_isolation_delete ON playlist
    FOR DELETE
    USING (trainer_id = current_setting('app.current_trainer_id')::bigint);
```

Identical four-policy block for `content_item`. `drill_detail` needs no
policy of its own — it carries no `trainer_id` and is only ever reached
through `content_item`.

## The token and payment ledger

Restates the seven invariants from architect-architecture.md "The token and
payment ledger — Invariants, as enforceable rules" as a single lookup table,
pointing at exactly where each is enforced (all mechanisms are specified in
full under `token_entry`/`token_balance` above; this is the index).

| Invariant | Statement | Enforced by |
|---|---|---|
| I1 | Balance projection = sum of that pair's entries | Not a DB constraint (spans two tables). `TokenLedgerService` maintains both in one transaction; a console command + test reconcile periodically |
| I2 | Balance never negative | `CHECK (balance >= 0)` on `token_balance` |
| I3 | Every `spend` records the beneficiary; every `refund` inherits it | CHECK requires the column on `spend`/`refund`; inheritance is `TokenLedgerService::refund()`, covered by a test |
| I4 | Sum of refunds against one spend never exceeds it | Lock the spend row (`SELECT ... FOR UPDATE`, no-op write), then sum + compare, inside the transaction — cannot be a running counter because I7 forbids `UPDATE` |
| I5 | Sign matches kind | CHECK on `token_entry.amount` vs. `kind` |
| I6 | At most one entry per (payment record, purpose) | Partial unique index `(payment_record_id, kind) WHERE payment_record_id IS NOT NULL` |
| I7 | No entry ever updated or deleted | `REVOKE UPDATE, DELETE ON token_entry FROM pp_app` |

### Lock ordering, as repository methods

Architecture's fixed order — **token balance row, then event row** — is made
structural by funnelling every dual-lock path through two repository
methods that can only be called in that order:

- `TokenBalanceRepository::lockForUpdate(int $trainerId, int
  $parentAccountId): TokenBalance` — always called first.
- `EventRepository::lockForUpdate(int $eventId): Event` — always called
  second, only from inside a transaction that already holds the balance
  lock.

Both a paid RSVP and an RSVP-cancellation refund go through
`TokenLedgerService`/`RsvpService` in that order; a test drives both
concurrently against the same parent and event and asserts no deadlock
(architecture "Risks" already names this exact test).

Trainer-initiated cancellation never holds both locks at once (architecture
"Trainer cancellation refunds"): it locks and commits the `event` cancel
first, then refunds each player asynchronously in the worker, one
transaction per RSVP, each taking only that one balance lock — the fan-out
described under architecture "Synchronous and asynchronous work".

## Money and the platform fee

Integer minor units throughout (architect-architecture.md "Stack"). This
section fixes the one thing the architecture doc explicitly deferred here:
**the rounding rule for the 5% platform fee**, since the trainer absorbs it
and it is included in the listed price (BR-05-7).

### Formula

```
platform_fee_minor_units = FLOOR(
    (amount_minor_units * fee_rate_basis_points + 5000) / 10000
)
```

Equivalently: round half up to the nearest minor unit (cent), computed
entirely in integer arithmetic — no floating point anywhere near a money
figure. In PHP:

```php
$feeMinorUnits = intdiv($amountMinorUnits * $feeRateBasisPoints + 5000, 10000);
```

### Verified against both worked examples in the epic

- BR-05-7: $100 event, 5% (500 bps) → `intdiv(10000*500 + 5000, 10000) =
  intdiv(5005000, 10000) = 500` → **$5.00 exactly**, matching "the $5 (5%)
  platform fee" stated in the epic.
- AC-05-11: $20 charge, 5% → `intdiv(2000*500 + 5000, 10000) =
  intdiv(1005000, 10000) = 100` → **$1.00 exactly**, matching "a platform fee
  of $1 (5%)".
- A genuine half-cent case (10-cent amount, 5%): `intdiv(10*500 + 5000,
  10000) = intdiv(10000, 10000) = 1` — an exact 0.5-cent fee rounds up to 1
  cent, confirming round-half-up (away from zero), not banker's rounding.

### Where it runs

Computed once, at `payment_record` creation, from
`trainer_billing_settings.platform_fee_basis_points` **read at that moment**
and snapshotted into `payment_record.fee_rate_basis_points` and
`payment_record.platform_fee_minor_units`. AC-05-27 changes the rate for new
transactions only ("the new subscription rate applies from the trainer's
next billing cycle, and new transactions use the new fee rate immediately")
— a rate read live at *display* time would retroactively rewrite every
historical figure, which is exactly what the snapshot prevents.

`platform_fee_minor_units` is sent to Stripe as the Connect charge's
`application_fee_amount` — it is a request parameter the platform must
compute and hold, not a reporting figure, so storing it does not conflict
with the earnings boundary (architecture "The earnings boundary": no
*revenue/payout/earnings* figure is stored or summed locally — the fee
amount is an input to the Stripe call, not an output presented as revenue).

**Trainer net/payout is never computed or stored here.** Stripe deducts its
own processing fee (2.9% + $0.30) independently and that figure is never
mirrored locally — `StripeReportingReader` is the only source of any
earnings/payout figure shown to a trainer (architecture "The earnings
boundary"), read live, never cached.

## Doctrine mapping notes

`config/packages/doctrine.yaml` already fixes two decisions this section
builds on: `naming_strategy: doctrine.orm.naming_strategy.underscore`
(entity `ContentItem` ↔ table `content_item`, matching everything above),
and `identity_generation_preferences: PostgreSQLPlatform: identity` (every
`#[ORM\GeneratedValue]` resolves to `IDENTITY` with no per-entity strategy
argument needed).

### Entity and repository per table

One entity, one repository, in the owning module's `Entity/`/`Repository/`
directory per architecture "Module map" (`src/<Module>/Entity/`,
`src/<Module>/Repository/`) — the `mappings.App` block already points
`auto_mapping` at all of `src/`, so this needs no per-module Doctrine config,
only the directory convention itself. Table → entity is 1:1 for every table
above **except**:

- `drill_detail` maps as a **joined subclass** of `ContentItem` (Doctrine
  Class Table Inheritance: `#[ORM\InheritanceType('JOINED')]`,
  `#[ORM\DiscriminatorColumn(name: 'type', type: 'string')]`,
  `#[ORM\DiscriminatorMap(['video' => ContentItem::class, 'drill' =>
  Drill::class])]` on the parent, so a `video`-typed row hydrates as the
  base `ContentItem` and a `drill`-typed row hydrates as `Drill extends
  ContentItem` carrying `drill_detail`'s columns). This is exactly what the
  `type` discriminator and the `content_item_id`-as-shared-PK pattern are
  for.
- `account_profile` and `trainer_billing_settings` and
  `trainer_branding_settings` map as Doctrine `#[ORM\OneToOne]` owning-side
  entities with `#[ORM\Id]` on the FK column itself (shared-PK pattern), not
  embeddables — each has its own repository and its own lifecycle, unlike a
  true embeddable which has neither.

### Embeddables

Small, always-loaded-with-their-parent value groups map as `#[ORM\Embeddable]`,
not separate entities, since none of them are independently queried,
FK-referenced, or RLS subjects:

- `player_profile`'s `emergency_contact_name`/`emergency_contact_phone` →
  `EmergencyContact` embeddable.
- `event`'s `min_age`/`max_age`/`skill_levels`/`genders` →
  `EligibilityCriteria` embeddable.
- `event`'s `usd_pricing_enabled`/`usd_price_minor_units`/
  `token_pricing_enabled`/`token_price` → `DualPricing` embeddable, with a
  value-object method `priceFor(PaymentMethod $method): Money|TokenCount`
  used by the RSVP service instead of branching on raw columns at every call
  site.
- `coupon_redemption`'s three `*_price_minor_units` columns → a `Discount`
  embeddable exposing the BR-06-9 floor-at-zero invariant as a named
  constructor (`Discount::apply(Money $original, Coupon $coupon): self`)
  rather than three independently-settable properties.

### PHP enums vs. database enums vs. CHECK constraints

Every `VARCHAR` + `CHECK (col IN (...))` column above (see Conventions,
"Enums") maps to a **native PHP 8.1+ backed enum** on the entity side —
`Role`, `EventType`, `RsvpStatus`, `TokenEntryKind`, and so on, one per
distinct vocabulary, defined in the owning module (e.g.
`App\Billing\Entity\TokenEntryKind`). Doctrine maps each via
`#[ORM\Column(enumType: TokenEntryKind::class)]`, which DBAL translates
to/from the plain string column automatically — the CHECK constraint and the
PHP enum enforce the same closed vocabulary at two different layers (DB and
type system) without a third native-Postgres-enum layer that would need its
own `ALTER TYPE` migrations to extend.

Per architecture "Layering... Persistence and queries: read-heavy screens

### Rollback notes

Every migration above is written with a paired `down()` that drops what it
created, in reverse dependency order within the batch — standard for
Doctrine Migrations and not restated per-table. Two things need more care
than a bare `DROP TABLE`:

- **RLS-enabled tables**: `down()` must `DROP POLICY` before `DROP TABLE`
  runs (Postgres drops policies automatically with the table, so this is
  usually a no-op, but the migration should not assume the same is true for
  a table being *altered* rather than dropped — narrowing/widening a policy
  needs an explicit `DROP POLICY ... ; CREATE POLICY ...` pair, not an
  `ALTER POLICY` that silently leaves a gap between the two statements
  inside the same transaction).
- **Deferred-FK migrations** (M2–M7 attaching constraints created earlier):
  `down()` drops the constraint, not the column — the column still belongs
  to the earlier migration that created it.

### Backfill

No migration in this list runs against populated data — this is a schema
for an application that does not exist yet (`Task/app/src/Entity` is
currently empty). The one backfill worth flagging for whoever eventually
*does* run this against seeded/staging data: `player_profile.is_child`
(service-maintained, not generated — see that table) must be backfilled from
`parent_child_link` existence before the application starts trusting it, if
any fixture or import ever inserts `parent_child_link` rows without going
through `MembershipService`.

## Decisions

| Decision | Chosen | Rejected | Because |
|---|---|---|---|
| Primary key strategy | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | UUID v7; UUID v4 | `Task/app/config/packages/doctrine.yaml` already sets `identity_generation_preferences: PostgreSQLPlatform: identity` — real scaffolded infrastructure, not a style preference to relitigate. UUID's usual justification (opaque, unguessable public identifiers) does not apply here: every genuinely public, unauthenticated identifier in this platform (`share_link.code`, `form.shareable_slug`) is already a separate high-entropy token column, not the row's PK, so sequential PKs leak nothing through a public URL |
| Public token columns | Separate high-entropy `code`/`shareable_slug` VARCHAR, globally unique | Using the row's own PK as the public token | Keeps the PK-strategy decision above uncoupled from the "must be unguessable" requirement, which only two tables (`share_link`, `form`) actually have |
| Enum encoding | `VARCHAR` + `CHECK (... IN (...))` | Native `CREATE TYPE ... AS ENUM`; a lookup table per vocabulary | Native enums fight migrations (`ALTER TYPE ADD VALUE` transactional restrictions pre-PG12, still awkward to script idempotently); a lookup table is unjustified overhead for closed, small, code-reviewed vocabularies (contrast `skill_level`, which genuinely might need to be a lookup table later — see Open questions) |
| Money | `INTEGER` minor units | `NUMERIC`; `BIGINT` minor units | Architecture already settles minor units; `INTEGER` tops out at $21.4M/row, far above the $1–$10,000 range this platform ever charges in one transaction (AC-08-5) |
| Platform fee rounding | `FLOOR((amount*bps + 5000)/10000)` — round half up, integer-only | Banker's rounding; float multiplication then round | Verified exactly against both worked examples in the epic (BR-05-7, AC-05-11); floats are never acceptable near money; banker's rounding was not what either worked example implies |
| Capacity checks | `SELECT ... FOR UPDATE` + `COUNT(*)`, no cached counter | A maintained `current_rsvp_count`/`current_registration_count` column | A cached counter needs a correct decrement on every cancellation path (RSVP cancel, refund) or it silently drifts; `COUNT(*)` under a lock is always correct and cheap at capacity ≤ 999/1000 rows |
| Playlist/content soft delete | `deleted_at TIMESTAMPTZ NULL` | Hard delete with `ON DELETE SET NULL` on referencing FKs | The epic's own AC-04-36 explicitly recommends soft delete; it is also what makes BR-04-12's "reference breaks and shows Unavailable" implementable without an orphaned FK, since the referenced row still exists |
| Token ledger I4 (refund sum ≤ spend) | Lock the spend row (`SELECT ... FOR UPDATE`, no write), then sum + compare | A maintained `refunded_amount` counter on the spend row | I7 forbids `UPDATE` on `token_entry` at the database-privilege level — a counter column has no legal write path once the table is append-only |
| Token entry / audit log immutability | `REVOKE UPDATE, DELETE FROM pp_app`, applied per-table in the migration that creates it | A Doctrine-level "no setters" convention | Matches architecture Decisions exactly ("Entry immutability... a convention survives exactly until someone adds a setter"); the role separation RLS already requires makes this free, and `00-roles.sh` already documents this as the creating migration's responsibility |
| Coach cross-tenant uniqueness (BR-01-11) | Partial unique index `(account_id) WHERE status='active'`, no `trainer_id` in the key | An application-only check; a global `active_coach` table outside RLS | PostgreSQL unique-index enforcement is not filtered by RLS, so a partial unique index on a trainer-scoped, RLS-protected table still correctly rejects a second active membership from a different tenant's session — a real, deliberate use of a documented RLS property, not an accident |
| RSVP status vocabulary | `pending_parent_approval`\|`pending_payment`\|`confirmed`\|`canceled` — no `attended`/`no_show` | Epic-02 Data Requirements' literal `Registered/Canceled/Attended/No-Show` | The same epic separately defines a richer 4-state `AttendanceRecord` (BR-02-17), which architecture already makes its own entity; keeping both vocabularies would let RSVP and attendance state disagree about the same fact |
| Referral "Rewarded" state | Not stored; derived from whether a `token_entry(kind='referral_reward', referral_id=...)` exists | A third `referral.status` value | A stored flag and the ledger's own record of the grant could drift; the ledger is already the single source of truth for "was a reward actually granted" |
| `playlist_assignment` status | Not stored; derived by joining `content_progress` per player at read time | A `status` column on the assignment row | An assignment can target a label or skill-level group, so one status value per row cannot represent N players' individual progress; `content_progress` already tracks this more granularly, per the same epic's own Data Requirements |
| Form field definitions | `JSONB` array on `form`, matching the epic's own stated shape | A normalized `form_field` child table | Field types are a closed 4-value set (BR-08-2), fields are never queried individually anywhere in the epic, and the epic itself presents this as JSON (Data Model, lines 341-350) |
| `audit_log_entry.subject_id` | Untyped soft reference (`subject_type` + `subject_id`, no FK) | Real typed FK per possible subject | Audit subjects span nearly every entity in the system; `child_approval_request`'s three-shape polymorphism gets real FKs precisely because three is a manageable number of always-mostly-null columns and dozens is not |
| `FormSubmission` tenancy classification | Trainer-scoped, per architect-architecture.md | The tenancy manifest file's own header comment, which lists it as global | The settled architecture document is an explicit hard input; the scaffold comment is not one of the listed settled inputs and appears to predate this design stage. Flagged prominently at the top of this document and here so the contradiction is visible exactly once, not silently resolved |
| Pre-tenant resolution for `ShareLink`/`Form` codes | New global table `public_tenant_code`, per `specs/council-sharelink-tenant-resolution.md` option G | Reclassifying `ShareLink`/`Form` as global (council option D/E); resolving inside `MembershipService` (option B); routing through `CrossTenantReadService` (option F) | `ShareLink` and `Form` are correctly trainer-scoped, but RLS silently returns zero rows for an anonymous code lookup with no tenant set — a real gap this document's first draft left implicit. The council's option G is the narrowest fix: one global `code → trainer` mapping with no FK into either owning module, so `Platform` stays dependency-free while the two trainer-scoped tables keep their own expiry/status/analytics detail. Adopted here because the alternative was shipping a known, undocumented fail-closed-silence gap on the platform's most common signup path |
| Player/Parent single-role modeling | `player_profile.self_account_id` (nullable, unique) + `parent_child_link` (parent/child/optional child-login) | A `PlayerProfile` subtype per role; a single `is_parent` flag on `Account` | The epic explicitly declines to resolve this ("this spec does not resolve how that should be modeled" — Epic-01 Data requirements note). This is the schema-level resolution, flagged in Open questions as an assumption, not a settled fact, because no upstream input actually settles it |
| Content purchase beneficiary | `playlist_access_grant.player_id` required — one specific child, not the whole family | Grant scoped to `(trainer, parent_account)` only, usable by any child, mirroring tokens | Not stated either way by Epic-04/05. `content_progress` is already keyed per specific player, and A7's reasoning for tokens (record the beneficiary even though nothing requires it yet) generalizes naturally here. Flagged in Open questions as an assumption |

## Open questions

Genuinely unsettled by the specs. Not decided here — recorded so a later
session does not have to rediscover them.

1. **Player/Parent modeling** — Epic-01 explicitly states "this spec does
   not resolve how that should be modeled"
   (`requirements-analyst-epic-01-user-management-spec.md`, "Data
   requirements", note on line 302). This document adopts
   `player_profile.self_account_id` + `parent_child_link` (see Decisions) as
   a concrete, workable resolution, but it is this document's inference, not
   a settled fact — worth explicit confirmation before `architecture-implementer`
   scaffolds entities against it.

2. **Does a playlist purchase unlock for one child or the whole family?**
   Neither Epic-04 nor Epic-05 states this. Tokens are explicitly
   parent-trainer-scoped and spendable for any child (BR-05-2), but content
   access (`playlist_access_grant`) is modeled here as per-specific-player,
   consistent with A7's beneficiary-recording spirit and with
   `content_progress`'s existing per-player key. If the client's intent is
   family-wide unlock, `playlist_access_grant.player_id` would need to
   become nullable-meaning-"whole family" or the table restructured around
   `(trainer_id, parent_account_id)` instead.

3. **Skill level vocabulary (Q-01.01, still open).** This schema uses a
   plain `VARCHAR(50)` on `player_trainer_membership.skill_level` and
   `playlist.filter_skill_levels`, per Section B's safe default ("store as
   configurable, not hard-coded"). If the client wants trainer-configurable,
   reusable skill-level *definitions* (not just free text per membership),
   the upgrade path is a new trainer-scoped `skill_level_definition(id,
   trainer_id, code, label, sort_order)` lookup table with
   `player_trainer_membership.skill_level_definition_id` replacing the
   VARCHAR — a additive migration, not a redesign, since nothing else in
   this schema treats skill level as anything but an opaque string today.

4. **`ContentUsage` vs. "Usage analytics for public content creators" being
   out-of-MVP.** `requirements-analyst-epic-04-lp-content-spec.md` lists
   "Usage analytics for public content creators" under Phase 2 deferrals
   (line 647), yet architect-architecture.md's entity population explicitly
   requires `ContentUsage` and names the exact figure it backs ("the
   creator's 'used by N trainers' figure"), and the epic's own AC-04-37
   independently requires "top content creators" on the Epic-07 LPPP
   Analytics dashboard. This document builds `content_usage` per the settled
   architecture and treats AC-04-37's "top creators" ranking as the
   in-scope, narrower thing the broader deferred "usage analytics" bullet is
   not — but the tension between the epic's own out-of-scope line and the
   architecture's settled entity is real and worth the client's eyes, not
   silently resolved.

5. **Coupon code case-sensitivity.** BR-06 never states whether `coupon.code`
   should collide case-insensitively the way `label.name` explicitly does
   (BR-03-3). This schema leaves `coupon.code` case-sensitive (a plain
   `VARCHAR` unique index, no `citext`/`lower()` normalization) as the more
   conservative default for something typed into a checkout field, but
   flags it since the epic is silent rather than explicit either way.

6. **`duration_seconds` nullability on `content_item`.**
   `requirements-analyst-epic-04-lp-content-spec.md`'s own Open questions
   note "what happens if YouTube-based duration auto-detection is
   unavailable at video-add time" is unresolved by the epic. This schema
   makes the column nullable to accommodate that gap rather than inventing
   a fallback value (e.g. 0), which would be indistinguishable from a
   genuinely zero-length video.

7. **Whether Epic-07's dashboard metrics are ever materialized.** Per
   architecture "Open architecture risks" #5, this schema assumes live
   queries and provides no metrics-storage entity. If AC-07-41's performance
   targets prove unreachable live at 500 trainers/10,000 players, the first
   materialized projection this platform needs is a
   `dashboard_metrics_snapshot` table — deliberately not built ahead of a
   measured need.
